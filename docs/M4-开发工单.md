> 来源：策划案 §10.1A（目标与验收方式）+ 2026-10 的**相关度审查**（9 个系统逐个取证）。

## 0. 目标（用户拍板 2026-10）

> **把每一个方面都打磨到与「物品整理」这件核心玩法相关。**

细则见策划案 §10.1A。原来排在前面的那些方向（内容量、剧情、NPC 关系）
一律**降为次要** —— 不是不做，是不再占主要目标的位置。

**四个主要目标（按优先级）**：

| # | 目标 | 它具体是什么 |
| --- | --- | --- |
| 1 | **整理本身要有更多决定** | 现存的取舍集中在"放哪一格 / 贴什么清单 / 排不排 FEFO"。M4 要长出**新的整理维度** |
| 2 | **每个系统都要接回整理** | 逐条审查：灾难 → 它改的是"什么东西该放哪儿"吗？事件 → 它逼玩家重排吗？**接不回去的就改口径** |
| 3 | **整理成果要能被反复看见** | 整理的价值目前主要在**生存期日报**里兑现，要在更多地方被看见 |
| 4 | **整理的反馈要更细** | 声音、吸附动画、按下去的回应 —— 从"不难受"到"上瘾" |

**次要目标**：目标 4 与目标 1 抢工期时**先让步**（手感"不难受"就够）；
§10A 候补清单里与整理无关的条目**明确降级**；内容量继续灌算**常态推进**，不占目标位。

## 1. 规则（每条工单都要满足）

1. **每一条都必须能回答"它让哪个决定不同"** —— 答不出来的不做，或者改成"展示类"并说明；
2. **每条单独提交**，提交前 `npm run check` 全绿（**不许绕过**）；
3. **改了数值就写探针**，把实测数字写进策划案 §12 的实测表；
4. **加了守卫就故意让它失败一次**（纪律 §0.2）；
5. **动到界面 → 交付说明里写"硬刷新 + 期望看到什么"**（纪律 §0.3）；
6. 施工方法照纪律文档 **§4A 的六个套路**（探针先行 / 诊断先于猜测 / 接线审查 / …）。

## 2. ★★★ 需要用户拍板的五个决策（开工前）

前三条**不是工程问题**，它们各自会改变玩法的形状；后两条是 **2026-10 用户提的
「顺手位存在感」那个问题**拆出来的（详见第五组）。工单里凡是依赖它们的，
都标了「⛔ 前置」。

### 决策 A：多灾难怎么给入口

**现状**：数据层**已经完成**（116 场，7 个家族，`content/灾难/*.json` → `data/disaster.ts`，
M3-2 第 5 步 5d "116 场入库、换皮对 0"）。而**实机每一局都是寒潮**，因为两处硬编码：

```
src/systems/setup.ts:236   disasterId: M1_DISASTER_ID
src/systems/setup.ts:238   createStartingShelves(ROOM_ID, M1_DISASTER_ID)
```

**代价（已经量出来的）**：寒潮是**唯一没写空间维度**的那一场（L1 教学样板，只用 4 维），
所以 `capacityFactor`（43 场写了）与 `unusableShelfIds`（31 场写了）**一场都没生效过**。
而那是 17 个影响维度里**只有 2 个**会改变"什么东西该放哪儿"的其中一个。

**三个选项**：

| 选项 | 代价 | 它顺带解开什么 |
| --- | --- | --- |
| **① 随机抽一场** | 最小（改一行 + 开局页文案） | 115 场数据第一次被玩家碰到；`a_all_disasters`（见过 4 场）不再是空成就 |
| ② 开局页让玩家选 | 中（一个新界面 + 图鉴/成就的解锁口径要一起定） | 上面那些 + "先知知道该囤什么"这条身份设定要重新想（选之前就知道灾难，那"先知"还剩什么） |
| ③ 先不做，只把参数接对 | 最小（只改 `createStartingShelves` 的实参） | 只解开空间维度，其余 115 场仍然碰不到 |

★ **建议 ①**：它让一整维第一次生效，而"选灾难"会牵出一串要一起定的东西
（先知身份、图鉴解锁、`a_all_disasters`）。⚠ 但**用户是设计权威**，这条要问。

### 决策 B：生存期要不要有回整理页的路

**现状**：`systems/phases.ts:45` 是 `survival_day: ['survival_day', 'help_request', 'ending']` ——
**没有 `organize`**。`ui/SurvivalScreen.ts` 也只有 `start` / `next` / `trade-confirm` 三个动作。

**后果**：§12.3 那句"代价都可逆、都能爬回来"（v0.5 的核心承诺）
**只对 D-Day 之前那 7 天成立**。进了生存期，玩家只能看着自己烂掉的盘面。

⚠ 而 `survival.test.ts` 里那条"D+2 补救 → 撑过 14 天"的**永久回归探针**
是**直接改 `run` 状态**造出来的场景，玩家在真实界面里**做不到** ——
它验的机制没问题，但**不能被读成"玩家可以中途补救"**。

**这条要定的是"整理在生存期算什么"**：

- 如果**免费** → 整理变成无成本的万能解药，生存期的张力（`workCost` 那条链）当场失效；
- 如果**花行动点** → 与"再跑一趟店"直接竞争（那正是想要的取舍）；
- 如果**花体力** → 与"翻找"同一条账，但会与"体力见底"那条下坡路互相强化（可能太狠）；
- 如果**不做** → 那就应当**改 §12.3 的措辞**，把"窗口是有限的"写进宪法，
  并把那条探针的注释改成"这验的是机制，不是玩家的可达路径"。

★ **建议：花 1 行动点**。理由：行动点是**已经存在的资源**（`ACTION_POINTS_PER_DAY`），
"今天这 3 点，是再跑一趟五金店，还是回家把那两行重排一遍"是一个真取舍，
而且它不动体力那条已经调好的曲线。

### 决策 C：外界温度要留还是要删

**现状**：它的唯一读点是**显示**（`ui/SurvivalScreen.ts` 的"外面 / 里面"那一格），
没有任何逻辑读它。而 `data/disasterDimensions.ts` 的注释写着
"实际是必填，所以这一维永远算『用到』" ——
**校验器把一维零影响的字段当成实质维度在计数**（116 场每一场都白送一维）。

**两条路**：① 给它一个下游（最自然的是"外界温度 × 庇护所 → 屋内温度"，
再让屋内温度参与腐坏或体力恢复）；② 承认它只是表现，**把校验口径与注释改掉**。

★ **建议 ②**（这一轮先做），因为 ① 会动腐坏/体力两条已经调好的链；
而 ② 只是把那句"永远算用到"改掉，成本几分钟。

### 决策 D：顺手位要不要**每天都**参与

现状：`emergency`（应急可达率）**不进 `quality`**，所以它**不影响每天的翻找体力** ——
只在**体力 < 30 那天**硬性生效（取用 = `ceil(need×0.5)` + 顺手位件数）。
而"体力见底"在整理得好的档里很少发生 → **它的作用正好在你不需要它的时候才出现**。

| 选项 | 效果 | 代价 |
| --- | --- | --- |
| **① 不动数值**，只把"见底那天的依靠"提前预告 | 不碰任何基线 | 它是**提示**，"什么时候提示"要定 |
| ② 给 `emergency` 一个低权重进 `quality`（例如 ×0.15） | 顺手位**每天都**影响翻找体力 | 三个数（9 / 18 / 27）要重取，而它们是**三条永久回归探针**的基线 |

★ **建议 ①**（先做，见第五组解法 ② 的 B 口径）；
② 更彻底但**是一条独立的工单**，不该混在这次里。

### 决策 E：突发事件的出现率（或者说，内容量与出现率的比值）

现状：`EMERGENCY_CHANCE = 0.3` → 14 天碰到 **~4.2 次**，而池子里 **60 条** →
**一局只能见到 7%**。三个方向都对，但它们改的是不同的东西：

| 方向 | 14 天碰到 | 一局见到 | 代价 |
| --- | --- | --- | --- |
| 提到 0.45 | 6.3 次 | 11% | 突发从"像意外"往"像日程"靠。★ 这个常数**有过一次前科**：它原来按"7 条事件"反推，M3 加到 28 条时同一个常数让概率变成 **63%** —— 纪律 §3.10 就是那次 |
| 摊薄内容（降级那些兑现不了的） | 不变 | 比例上升 | 要删内容 |
| **都不改** | 4.2 次 | 7% | 存在感继续低，但"生日这类事件本来就该稀"是有道理的 |

★ 我没有建议 —— **这条是纯粹的设计取舍**（"稀而重"还是"常见而轻"），
要用户定。⚠ 若选"提高出现率"，**必须**同时改 `data/emergencies.ts` 的
`emergencyNoneWeight` 推导方式（它现在是从"当次池子的权重合计"反推的，
所以改 `EMERGENCY_CHANCE` 是安全的 —— 但要把那条注释里的历史一起更新）。

## 3. 工单

### 第一组：接线（**性价比最高，建议全做**）

> 这一组全是"代码通了、数据写了，而下游没人读"。
> 它们不改玩法形状，只是把已经承诺的东西兑现 —— 见纪律 §2.19。

#### ✅ W-01 ★★★ 把灾难的空间维度接上（**一行参数**）

`systems/setup.ts:238` 把 `M1_DISASTER_ID` 换成这一局真正的 `disasterId`。

- **它让哪个决定不同**：一场 `capacityFactor: 0.6` + `unusableShelfIds: ['shelf_a']`
  的局里，玩家开局就少一整块货架和底下一排 —— "棉被我放哪"从"随便"变成"只有这几个位置"；
- **现状**：43 场 / 31 场写了数据，**一场都没生效**；
- **顺手要修的（同一片区域的真 bug）**：`addFurniture` 的 `opts.spoilFactor`
  在生产路径上**从来没被传过**（`systems/home.ts:110`），而注释写着"与开局那三块用**同一把尺子**"。
  于是**买来的家具永远是满高** → 只要跑到一场 `capacityFactor < 1` 的灾难上，
  **100 元就能把灾难吃掉的空间买回来**。今天不发作只是因为只有寒潮。
- ⛔ **前置：决策 A**（哪怕只做选项 ③ 的"参数接对"也行）。

#### ✅ W-02 ★★ 让吸附优先落在"清单收它的那一行"

`ui/OrganizeScreen.ts` 的 `nearestLegalSlot` 合法判据只有**空格 / 同类 / 会互换** ——
全文**没有一次** `zoneListedFor`。所以"贴了主食的那一行"和"什么规矩都没写的行"
在**手感上完全等价**。

- **改法**：候选排序里加一个键 —— 同类候选里优先挑清单收它的那一行。
  **只改"优先"，不阻止、不提示、不标红**（§5 引擎①那条"游戏不评判对错"一字不动）；
- **它让哪个决定不同**：玩家自己写的那张胶带**第一次开始替他做决定**；
- ⚠ 这一条**几乎零风险**（不改数值、不改分数、不改判定），
  而它把引擎②从"放大器"变成"**引擎① 的放大器**"。

#### ✅ W-03 ★★ 成就与图鉴：从"见过 / 拥有"改成"整理过"

15 条成就里只有 **2 条**与整理直接相关，而 `a_spotless` 要求**14 天每天两率满分**
（近乎不可达）；图鉴点亮条件是**拥有**（`systems/codex.ts` 连没拆的纸箱一起数）。

- **加中间档**：`cleanDays >= 7`（半程）。`cleanDays` 已在逐日计数，**不需要新埋点**；
- **图鉴加第二档**：这件物资**曾被放在明确接收它的清单上**（`zoneListedFor` 是现成判定，
  与归位率同一把尺子，不会造出第二个真相来源）；
- **`a_never_unreachable` 拆开**：它的判据混了两件事（**没体力**与**没放顺手位**）；
- **它让哪个决定不同**："中途整理一次值不值"、"新东西先塞箱子还是先想清楚归哪一行"。

#### ✅ W-04 ★ 补齐"说了没接"的其余几处

| 处 | 现状 | 改法或删掉 |
| --- | --- | --- |
| `categoryEfficiency` 的恢复侧 | 代码自己写着"🚧 尚未接线"，而灾难文案在卖这个效果 | 接上 `healOf` / `shelterOf`，或者把文案改成不承诺 |
| `keepsake` tag | **全仓零读取**（"整理期摆放回心情"） | 接线（奢侈品这一类现在只有"贵+占地方"），或删掉承诺 |
| `floor` 家具 | 数据里有（12 格、0 元），**购买入口把它滤掉** | 接上（"0 元 / 12 格 / 会被进水类灾难吃掉"），或删掉数据 |
| `specialMechanics` | 引擎零读取、数据 0 场填写 | 立项，或在策划案里标成"以后"，并删掉字段 |

### 第二组：把"数值轴"接成"位置轴"（M4 的正题）

#### W-05 ★★★ 让事件从"加减数字"变成"改盘面"

169 个事件里 **104 个**会往家里加货、**65 个**只动四维与现金，
而**没有一个**改变已有物资的归属。真正会动货架的只有 `model/scatter.ts`（同一行内、不碰胶带）。

两个具体口子：

- **`stockCut` 只削商店、不碰玩家家里**（而且 169 个事件里 **0 处使用**）。
  补一个**会打到玩家家里**的效果，例如"楼下车库进水，最下面那一排泡了" ——
  `setup.ts` 的注释早写好了那个叙事（"进水/结冰/塌方都是**从下往上**吃掉空间"），
  只是从来没兑现过。**它让哪个决定不同**：**"低处放什么"**第一次成为可后悔的决定；
- **加一类新效果** `relocate` / `zoneBreak`（打散某一行 / 撕掉某一行胶带）。
  **它让哪个决定不同**：玩家会开始问"**哪一行即使被撕掉胶带我也不心疼**" ——
  这个决定**现在完全不存在**，因为胶带永远安全。

#### W-06 ★★ 给 1~2 个身份一条整理向的天赋

10 个身份的天赋**全是** `categoryDiscount`（唯一执行点 `systems/shop.ts`），
而 `data/identities.ts` 自己写着"失衡红线：只要『囤什么都行』成立，整理就失去意义"——
现状是**所有身份都在改"囤什么划算"，没有一个改"整理划不划算"**。

- **改法**：扩 `PerkRule` 加一个成员（例如 `{ kind: 'workCostFactor'; rate: 0.8 }` 装卸工、
  或 `{ kind: 'extraHandySlot' }` 小区保安）。`workCostOf` 的读点**只有 2 处**，接线面很小；
- ⚠ **不要加进熟练度等级**：`systems/identity.ts` 明写"等级**只改开局条件、不改单局中的任何公式**"，
  而那条约束是**为了三条永久回归探针**立的 —— 动它要一并处理探针口径。

#### W-07 ★★ 家具：拆掉两个"没有取舍的决定"

**① 冰箱严格支配另外两种**：冰箱 0.4 / 柜子 0.75 / 货架 1.0，而三者**同价（100）同格（24）**。
而 `data/furniture.ts` 那句 `why` 写的"装鲜食能多撑一阵，**装别的占地方**"——
那个代价**在代码里不存在**。

**② 而它的期望收益可以精确地是 0**（实数）：记 `D = E / spoilRate`（这件货在普通货架上还能撑几天），
14 天窗口里 `5.6 < D ≤ 10.5` 才**只有冰箱救得回来**；`10.5 < D ≤ 14` 时柜子与冰箱**等价**；
`D > 14` 时货架与冰箱**等价**。**冰箱相对柜子的优势只活在一个 4.9 天宽的窗口里。**
而实机每一局都是寒潮（`spoilRate 0.5`）→ 最短鲜食在普通货架上也活得过 14 天。

**两条便宜解法**（都顺）：

- 给冰箱一个代价（`h: 3` = 18 格，或价格抬到 140）—— "买保护"与"买地方"第一次成为同一笔钱的两个用途；
- 给灾难加一个 `fridgeDead`（断电类灾难里冰箱按 1 算）——
  ★ 它**不是新发明的叙事**：`data/disaster.ts` 的 notes 已经写着"外面转暖，**室内外冷藏链同时断**"、
  "**冰箱停摆**让腐坏加速"。把已经写好的话变成机制就够了。

#### W-08 ★ 反差层：把"囤得多"和"囤得好"分开

那四格的输入**没有一个来自整理系统**（`(day, disasterId)` / `(shelter)` /
`(货架∪**纸箱**的件数, 日耗)` / `(day)`）。最要紧的一条：`supplyDays` 把**货架与纸箱加总**，
所以"把 30 罐从纸箱搬到贴好胶带的架上"在这块屏幕上**一个数都不变**；它也不读到到期日。

- **最便宜的一条接线**：加一个同源函数，件数只数"按取用顺序真的够得到的那部分"
  （极限情况就是 `countOnHandy`），在日报加一格"**随手够得到 N 天**"；
- **它让哪个决定不同**：**"搬上架 / 贴胶带 / 标顺手位"这三个动作今天在日报上完全不可见** ——
  改完会在玩家每天必看的那一屏上直接变成天数差。

### 第三组：整理本身的新决定（目标 1）

#### W-09 ★★ 生存期回整理页（= 决策 B 的落地）

见决策 B。⛔ **前置：决策 B**。

#### W-10 ★★ 「一袋米占四格」—— 物资的物理大小

`ItemDef.slotSize`（1=小件 / 2=大瓶 / 4=整袋）原来就是为它留的位子，
而它**从来没有生效**（大米和电池占同样一格），所以 2026-10 把它删了
（见 D-07 的清偿记录）。**方向没丢，只是它不属于 M3。**

- **它让哪个决定不同**："一袋米占掉四格，值不值"—— 一个**现在不存在**的取舍，
  而它恰好是本作的核心动作（把东西塞进有限的空间）；
- ⚠ **代价要提前说清**：它同时动**放置 / 合并 / 拖动 / 容量 / 存档**五处，
  而且"一格一栈"这个前提一松，`slotSize` 会在**全表 121 件**上重新变成平衡问题。
  **一次机制级改动，不是给一个字段接线。**
- 参考：`docs/囤货末世-实施记录.md` 的候补清单第 5 条。

#### W-11 ★ 求援订单：让"从哪一行拿"成为一个选择

- 交付加**来源**（`from: 'shelf' | 'box'`），成本按来源算：
  贴了清单那一行 → 1.5/件；没写清单的行 → 3.3/件；纸箱 → 4.5/件。
  `model/consume.ts` 已有现成的 `RANK_IN_PLACE / RANK_SHELF / RANK_BOX` 三级判定；
- 加一条豁免：当日 `placement >= 1` → 本单**免体力**，界面明写"你这单不用翻"
  （`placement >= 1` 已经是「不翻乱」的现成门槛，口径可复用）；
- ⚠ 现有的**全屋口径要保留**（`systems/help.ts` 说那是刻意的"同一种劳作"），
  这一条是**加**一个行级选项，不是替换；
- **它让哪个决定不同**："现在拆箱省时间，还是翻我划好的那一行省体力"。

### 第五组：★ 顺手位的存在感（用户 2026-10 提的问题）

> 用户的原话：
>
> > "顺手位的作用目前来看还是不够明显，因为你的那些事件我基本都没怎么见过，
> >  很那见到，需要顺手位的也很少，事件在我从你的代码里看是很多，
> >  但是出现率和存在感太低了，而且事件比如小侄女要奢侈品这种他并不会给我任何好处，
> >  顺手位有没有又怎么样呢，怎么平衡解决一下这个问题"

这一组是**四条主张**的对照实验结果。★ 其中**两条被数据推翻、三条被证实** ——
而证实的那三条指向同一个结论：**不是"要不要顺手位"，而是"玩家感觉不到它起作用"**。

#### 实测（2026-10，`EMERGENCY_CHANCE = 0.3`，生存期 14 天）

| 用户的说法 | 实测 | 判定 |
| --- | --- | --- |
| 事件很多 | **60 条**突发（medicine 9 / fuel 10 / tool 11 / warmth 7 / food 9 / water 6 / luxury 8） | ✅ 成立 |
| 出现率和存在感太低 | 每天 30% → **14 天只碰到 ~4.2 次**；一局能见到的比例 **7%** | ✅ **成立，而且是最硬的一条** |
| 需要顺手位的很少 | **60 / 60 条都需要**（`needOnHandy` 是它唯一的判据） | ❌ **不成立** |
| 小侄女要奢侈品却不给好处 | **60 条里带奖励字段的：0 条** | ✅ 成立（而且这是**刻意的**，见下） |
| "顺手位有没有又怎么样" | 它**不进 `quality`**（`quality = 归位×0.6 + 临期×0.4`）→ **不影响每天的翻找体力** | ✅ **成立** |

#### 根因（三条，都是"感觉不到"，不是"没有用"）

1. **好处是"什么都没发生"**。化解一件突发的全部回报是**避免** `lost`（扣四维）——
   没有正收益。所以玩家在屏幕上看到的是"今天挺平静"，而不是"我的顺手位救了我"。
   ⚠ 而这是**刻意的**：§5 引擎①"游戏不评判对错"要求系统不夸、不评分。
   **修法不能是"加分"，否则会变成系统在打分。** 只能是"**让本来会发生的事可见**"（见解法 ①）；
2. **它在日结的账里不参与**。`organizeQuality` 只吃 `placement` 与 `fefo`，
   所以顺手位**不影响每天那 9 / 18 / 27 点的翻找体力**（那才是玩家每天都在读的数）。
   它只在**体力 < 30 那天**硬性生效（取用 = `ceil(need×0.5)` + 顺手位件数）——
   而"体力见底"在整理得好的档里**很少发生**。于是它的作用正好在**你不需要它的时候才出现**；
3. **一局见不到几条**。4.2 次 × 每次只占一屏 —— 而 60 条内容平摊下来，
   玩家**三局才能见到同一件**。存在感低是**内容量与出现率的比值**问题。

#### 解法（三条**独立**的，可以只做其中一条；每条都标了它动什么）

**解法 ①：让"本会发生的事"在日报上留一行（★ 最便宜，且不违反"不评判"）**

不化解与化解都写清**代价的形状**，而不是只报"没事"：

```
现在（不化解）：  夜里暖气管冻裂了，顺手位上只有 1 件燃料，不够。     ← 有信息
现在（化解）：    夜里暖气管冻裂了，顺手位上有 3 件燃料，用上了。     ← 有一行
★ 但它**没写"要不是你放了就惨了"**
```

**改法**：化解时补一句**反事实的陈述**（不是夸奖，是陈述）：
"……用上了。（这一格要是空的，今晚要掉 2 点健康）"。
★ 它符合 §5 的口径：**陈述事实，不夸玩家**；而它把"什么都没发生"翻译成了
"**本来会发生的那件事**" —— 这正是"零台词的反差层"（§6.6）那套手法。

- **它让哪个决定不同**："我今天要不要花两分钟把药从第二行挪到门口" ——
  玩家第一次能**看见**那件事的价钱；
- **成本**：小（一处文案 + 一个已有字段 `lost`）；
- ⚠ 注意：不要在**没化解**时也说教（那已经是惩罚了）。

**解法 ②：把"顺手位"从"只在体力见底时生效"变成**每天都参与一点**

现状是 `emergency` 不进 `quality`。两个口径可选（**要用户拍板**）：

| 口径 | 效果 | 代价 |
| --- | --- | --- |
| **A. `emergency` 进 `quality`（给一个低权重，例如 ×0.15）** | 顺手位**每天都**影响翻找体力 → 玩家每天都能感到它 | 会改变已经调好的体力曲线（9 / 18 / 27 三个数要重取），而那是三条永久回归探针的基线 |
| **B. 只把"见底那天的取用"提前预告** | 日报在体力接近 30 时提示"再掉几点头顶那格就是你唯一的依靠" | 不碰数值；但它是**提示**，与 §5"整理期完全静默"的边界要重新想（生存期有日报，所以不违规） |

★ **建议 B**：它不动那三条已经验证过的探针，而"预告"本身就是"让决定可见"。
⚠ A 更彻底，但要重跑探针并重定门槛 —— 那是**一条独立的工单**，不该混在这次里。

**解法 ③：把出现率提上去，或者把内容量摊薄（**要用户拍板**）**

数字摆在这儿，两个方向都对，但它们**改的是不同的东西**：

| 方向 | 做法 | 14 天内碰到 | 一局能见到的内容 | 代价 |
| --- | --- | --- | --- | --- |
| **提高出现率** | `EMERGENCY_CHANCE` 0.3 → 0.45 | 4.2 → **6.3 次** | 7% → **11%** | 突发从"像意外"往"像日程"靠（`data/emergencies.ts` 的注释明确说过"它要像意外，不能像日程"）。★ 而且**这个常数有过一次前科**：它原来按"7 条事件"反推，M3 加到 28 条时同一个常数让概率变成 63% —— 纪律 §3.10 就是那次 |
| **摊薄内容** | 60 条里**降级**那些"不可兑现"的（见下） | 不变 | 比例上升 | 要删内容 |
| **什么都不改** | 承认"14 天见 4 条"就是设计（节日/生日这类事件本来就该稀） | 4.2 次 | 7% | 存在感继续低 |

★★ **而奢侈品那 8 条自成一个子问题**（用户的例子正是它）：
`luxury` 不参与生存数值（`data/items.ts` 的注释写着"不参与生存数值：`nutrition` 全空、
不是任何灾难的 `priorityCategories`"），而 `keepsake` 承诺的"摆放回心情"**全仓零读取**（D-29）。
所以"小侄女要奢侈品"的**兑现是空的**：

- 对她：给了也换不到任何东西（`consumes` 只是拿走）；
- 对你：**可以拒绝**，而拒绝的代价只是 `lost` 里那 1~2 点心情 —— 而心情是四维里
  **最便宜**的一项（睡觉就回）；
- ★ 于是这 8 条突发**在博弈上是"永远拒绝"** —— 这不是 bug，是**没有设计的后果**。

**这一条的建议**：要么给 `luxury` 一条真兑现（`keepsake` 接上线：**摆出来的纪念品回心情**，
那样"给她一罐可可粉"就真的**有代价**了），要么把这 8 条改成"**她要的东西对你有用**"
（那就回到普通品类）。⛔ 它依赖 **W-04 里 `keepsake` 那条**。

#### 这一组要用户拍板的点（三个）

1. **解法 ② 选 A 还是 B**（进 `quality` 动探针基线 / 只做预告）；
2. **解法 ③ 选哪个方向**（提高出现率 / 摊薄内容 / 都不改）；
3. **奢侈品那 8 条**：接线 `keepsake`（让它真的有代价）还是改需求品类。

#### 这一组的验收口径（能用断言量的）

- [ ] **每一条化解之后，日报里能读到"本来会发生什么"**（现在读不到）——
      可写成"化解与不化解两种情况下，日报都含那件事的代价陈述"；
- [ ] **顺手位对"我今天该干什么"的影响可量**：至少一条路径上，
      玩家能在**当天**（而不是体力见底那天）因为顺手位而改变一个动作；
- [ ] 若采纳解法 ③：**一局能见到的突发事件比例从 7% 提到 ≥10%**（可写成探针）；
- [ ] 奢侈品那 8 条：**"给"与"不给"两个选择的期望差不为零**
      （现在给 = 白给，所以是零差 —— 可用三局探针对比）；
- [ ] ★ **反的一件事**：顺手位的改动**不许**让"好档"的体力曲线漂
      （除非明确采纳解法 ②-A，那时三条永久回归探针的门槛要一并重取）。

## 4. 建议的执行顺序

```
决策 A（多灾难入口）            ← 一行参数换一整维生效，而且解开最多东西
  └─ W-01  空间维度接上 + addFurniture 的 capacityFactor
  └─ 顺带：决策 C（温度那维的口径）—— 几分钟的事，一起做

W-02  吸附优先落在清单收它的那一行   ← 零风险、手感立刻不同
W-03  成就与图鉴改成"整理过"        ← 不需要新埋点
W-04  补齐"说了没接"的其余几处

顺手位第一刀（第五组 · 解法 ①）     ← 只改一处文案：化解时说出"本来会发生什么"
  └─ 它最便宜，而且是"让已有机制被看见"那一类（与 W-02 同一个性质）
  └─ 决策 D（顺手位要不要每天都参与）+ 决策 E（出现率 / 摊薄 / 都不改）

决策 B + W-09  生存期回整理页       ← 动 §12.3 的核心承诺，要用户点头
W-06  身份加整理向天赋
W-07  家具的取舍（冰箱的代价 / fridgeDead）
W-08  反差层接上整理量
W-05  事件改盘面                     ← 最大的一块，放后面

W-10 / W-11（机制级）与 W-12（展示）按剩余工期排
```

★ 顺序的两条依据：

- **"接线"排在"新增"之前** —— 那 6 处"承诺了但没接线"是**已经写好的东西**，
  兑现它们的单位收益最高（纪律 §2.19）；
- **"让已有机制被看见"排在"改机制"之前** —— 顺手位那一组的三条解法里，
  ①（说出"本来会发生什么"）不动任何数值，而 ②③ 都要重取探针基线或改内容量。
  先做①，再看还剩多少问题 —— 很可能①一做，②③ 就不需要了。
