## 0. 目标（用户拍板 2026-10）

> **把每一个方面都打磨到与「物品整理」这件核心玩法相关。**

细则见策划案 §10.1A。原来排在前面的那些方向（内容量、剧情、NPC 关系）
一律**降为次要** —— 不是不做，是不再占主要目标的位置。

**四个主要目标（按优先级）**：

| # | 目标 | 它具体是什么 |
| --- | --- | --- |
| 1 | **整理本身要有更多决定** | 现存的取舍集中在"放哪一格 / 贴什么清单 / 排不排 FEFO"。M4 要长出**新的整理维度** |
| 2 | **每个系统都要接回整理** | 逐条审查：灾难 → 它改的是"什么东西该放哪儿"吗？事件 → 它逼玩家重排吗？**接不回去的就改口径** |
| 3 | **整理成果要能被反复看见** | 整理的价值目前主要在**生存期日报**里兑现，要在更多地方被看见 |
| 4 | **整理的反馈要更细** | 声音、吸附动画、按下去的回应 —— 从"不难受"到"上瘾" |

**次要目标**：目标 4 与目标 1 抢工期时**先让步**（手感"不难受"就够）；
§10A 候补清单里与整理无关的条目**明确降级**；内容量继续灌算**常态推进**，不占目标位。

## 1. 规则（每条工单都要满足）

1. **每一条都必须能回答"它让哪个决定不同"** —— 答不出来的不做，或者改成"展示类"并说明；
2. **每条单独提交**，提交前 `npm run check` 全绿（**不许绕过**）；
3. **改了数值就写探针**，把实测数字写进策划案 §12 的实测表；
4. **加了守卫就故意让它失败一次**（纪律 §0.2）；
5. **动到界面 → 交付说明里写"硬刷新 + 期望看到什么"**（纪律 §0.3）；
6. 施工方法照纪律文档 **§4A 的六个套路**（探针先行 / 诊断先于猜测 / 接线审查 / …）。

### 决策 A：多灾难怎么给入口 —— ✅ **已拍板（2026-10 用户）**

**用户的选择**：**选项 ① 随机抽一场**（"改一行 + 开局页文案"）——
让 43 场写了却从未生效的空间维度第一次生效。

⚠ 落地的两个细节（都要写进开工第一条）：

1. **开局页文案要跟着改** —— `ui/PrologueScreen.ts` 现在显示的是**寒潮那场**
   （它只读 `M1_DISASTER_ID`）。抽到别的灾难时，那页的日历/温度/刚需品类都要跟着那场走；
2. **"先知"这个身份设定不受影响**（选项②才会动它）：玩家在开局页**就知道**自己抽到了哪一场，
   所以"先知知道该囤什么"仍然成立 —— 这也是选①而不是②的一个好处。

**现状**：数据层**已经完成**（116 场，7 个家族，`content/灾难/*.json` → `data/disaster.ts`，
M3-2 第 5 步 5d "116 场入库、换皮对 0"）。而**实机每一局都是寒潮**，因为两处硬编码：

```
src/systems/setup.ts:236   disasterId: M1_DISASTER_ID
src/systems/setup.ts:238   createStartingShelves(ROOM_ID, M1_DISASTER_ID)
```

**代价（已经量出来的）**：寒潮是**唯一没写空间维度**的那一场（L1 教学样板，只用 4 维），
所以 `capacityFactor`（43 场写了）与 `unusableShelfIds`（31 场写了）**一场都没生效过**。
而那是 17 个影响维度里**只有 2 个**会改变"什么东西该放哪儿"的其中一个。

**三个选项**：

| 选项 | 代价 | 它顺带解开什么 |
| --- | --- | --- |
| **① 随机抽一场** | 最小（改一行 + 开局页文案） | 115 场数据第一次被玩家碰到；`a_all_disasters`（见过 4 场）不再是空成就 |
| ② 开局页让玩家选 | 中（一个新界面 + 图鉴/成就的解锁口径要一起定） | 上面那些 + "先知知道该囤什么"这条身份设定要重新想（选之前就知道灾难，那"先知"还剩什么） |
| ③ 先不做，只把参数接对 | 最小（只改 `createStartingShelves` 的实参） | 只解开空间维度，其余 115 场仍然碰不到 |

★ **建议 ①**：它让一整维第一次生效，而"选灾难"会牵出一串要一起定的东西
（先知身份、图鉴解锁、`a_all_disasters`）。⚠ 但**用户是设计权威**，这条要问。

### 决策 B：生存期要不要有回整理页的路 —— ✅ **已拍板（2026-10 用户）**

**用户的口径（原话）**：

> "可以自由回去，并且做出操作也会有影响，只是不能通过商店补货了
>  （其他方式当然可以，而且给这个阶段获取的现金也提供一点作用，但是要合理）"

★ 补充拍板（同一天，紧接着）：

> "不要花现金加家具，生存页回去的时候闭合这个入口"

**所以这一条的形状是**：

| 项 | 口径 |
| --- | --- |
| 回去 | **自由**（不限次数、不需要先花资源买许可） |
| 操作 | **有影响** —— 整理、贴胶带、排 FEFO、标顺手位全都照常生效（它们本来就走同一套 `systems/organize.ts` 的命令） |
| 采购 | **商店关闭** —— 生存期不能补货。这与 §6.4 的世界观一致（囤货期是最后的采购窗口） |
| 家具 | ★ **入口闭合** —— 回整理页时**不给"加家具"**（`ui/OrganizeScreen.ts` 的 `addFurnitureHtml` 在生存期不渲染）。用户明确要求 |
| 现金 | **要给这个阶段赚到的现金一个合理的出口**（见下） |

⚠ **而"回去"必须有代价，否则它会毁掉生存期的张力** —— 这不是用户的额外要求，
是 §12.3 那条已经成立的账：`workCost`（每天 9 / 18 / 27 点翻找体力）之所以有意义，
是因为"整理得好"与"整理得烂"在**14 天里**分岔。**若回去免费且无限次，
玩家可以在体力见底的当天回去把整个盘面重排一遍** —— 那条下坡路就不存在了。

**建议的代价（要用户点头）**：**每次回去花 1 行动点**。
理由：行动点是**已经存在的资源**（`ACTION_POINTS_PER_DAY`），而且它现在只花在进店
（`systems/shop.ts`）—— 生存期商店关了，那 3 点行动点**本来就没有别的用途**。
于是它天然变成"**今天这 1~3 点：回去整理两行，还是留着做别的**"。
★ 它不碰体力/健康那几条已经调好的链，所以**不会让三条永久回归探针漂**。

**关于现金（用户要求"合理"）** —— 现状与选项：

现在生存期的现金**只有一个出口**：整理页加家具（`systems/organize.ts:930` 扣 100 元）——
★ 而用户刚刚**把这个入口关了**，所以**现金在生存期会变成 0 用途**（这是必须解决的）。

**已有的两条"其他方式"**（用户说"其他方式当然可以"）：

- **求援订单**（`systems/help.ts`）现在只收**货**（`demands` 是 `{category, count}`），
  而 `thanks.cash` 是**对方给你的**。所以现金**进不去**这条线（除非新增"用钱顶货"的口径，
  而那会削弱"整理得好才拿得出东西"这条核心）；
- **硬撑交易**（`systems/trade.ts`）是**以物易物**：3 件换 1 箱粮油（`TRADE_COST_PIECES = 3`）。

**所以我建议的出口是"给以物易物补一条现金通道"**（要用户点头）：

| 选项 | 做法 | 它让哪个决定不同 | 代价 |
| --- | --- | --- | --- |
| **① 交易能一半现金一半货**（建议） | 3 件的额度里，**1 件可以用现金顶**（按当日物价折算） | "我该把最后的罐头留着，还是花 80 块抵掉一件" | 要定折算价（`priceSurcharge` 已经在算当日物价，可复用） |
| ② 交易降价：给现金能少给一件 | 3 件 → 现金够时 2 件 | 同上，但更粗 | 更简单 |
| ③ 现金换"情报" | 用现金向 NPC 买一条先知日历的预告（接 D-13 的 `intel`） | "这一局该不该花钱知道后面几天" | 情报现在只在生存期**跨局**有用，本局内价值弱 |
| ④ 什么都不做，让现金在生存期真的没用 | —— | 没有 | ⚠ 与用户"要合理"的要求相反；而它会让"生存期赚到的现金"变成一个**只涨不用的数** |

★ **建议 ①**（与 `帮不了` 那条"对方留下的东西"对称：一个给、一个收），
但**要用户拍板**：它动的是硬撑交易的定价，而那是 §12.3 v0.6 调过的。

⛔ **依赖**：W-09（生存期回整理页）就是这条的落地。它顺带要改三处：
`systems/phases.ts` 的流转表、`ui/SurvivalScreen.ts` 加"回家整理"的入口、
`ui/OrganizeScreen.ts` 在生存期不渲染加家具。

### 决策 D：顺手位的事件要**更显眼 + 有回报** —— ✅ **已拍板（2026-10 用户）**

**用户的口径（原话）**：

> "顺手位的重点是让跟他有关的那些事件更显眼一点，
>  且能给我带来收益或者有趣的剧情或者成就解锁或者全都有"

★ 这句话把重心**从"改机制"挪到了"改内容与反馈"** —— 而它比"调权重"更对：
下面那三条根因里，**"好处是'什么都没发生'"**才是最要命的那条。

**所以这一条要一起做四件事**（前三件是用户点名的，第四件是它的前提）：

| # | 做什么 | 为什么 |
| --- | --- | --- |
| ① | **让事件本身显眼** | 现在它只是日报里的一行（`survival.ts` 的 `run.log`）。事件的正文其实已经写进日志了（"夜里暖气管冻裂了，顺手位上有 3 件燃料，用上了。"），**但它在日报那一堆行里没有分量** |
| ② | **给回报**（用户第一个点的） | 化解现在只换来"没掉血" —— 零正收益 |
| ③ | **给剧情 / 成就**（用户另外两个点的） | 成就现在 15 条里**只有 2 条**碰整理，而且**没有一条**与顺手位/突发事件直接挂钩（`a_all_handy` 读的是 `emergencyHurtCount`，那是"没受伤"而不是"用上了"） |
| ④ | **让"本来会发生的事"可见**（原解法 ①） | ★ 它是 ②③ 的**前提**：如果不先说清"顺手位救了你什么"，那 ②③ 的回报会显得**凭空掉下来** |

**② 回报怎么做 —— 三条路，都要避一个坑**：

⚠ **坑**：§5 引擎①"游戏不评判对错"要求系统**不夸、不评分**。
所以**不能**做成"顺手位上有货 → 加心情 X 点"那种**计分**（那会变成系统在打分，
而且玩家会开始刷它）。合口径的三种：

| 路 | 形状 | 它让哪个决定不同 |
| --- | --- | --- |
| **A. 收益是"省下来的"** | 化解时的 `lost` 本来会扣四维 —— 把它**明确写出来**（"要不是这一格，今晚掉 2 点健康"），并让`紧急可达率` 进日报的第一屏 | "我今天要不要花两分钟把药挪到门口" |
| **B. 收益是一件东西**（推荐做 1~2 条） | 少数事件化解后**对方留下点东西**（与求援的 `thanks` 同一个机制：现金 / 一小箱 / 一条情报） | "这次我拿得出来，值不值得拿" |
| **C. 收益是剧情 / 成就**（用户点名） | 新增 2~3 条成就：连续 N 天不让突发事件得手、在顺手位备齐过全部应急品类、某一条特定 NPC 事件的后续 | "为了那条成就，我愿不愿意腾出门口那一块" |

★ **建议都做**（用户说"或者全都有"）：A 是文案（最便宜）、B 加 1~2 条事件的效果字段、
C 加 2~3 条成就（**不需要新埋点** —— `emergencyHurtCount` 与 `countOnHandy` 都在跑）。

**③ 剧情怎么做 —— 一条具体的形状**（不新增系统，复用求援那套）：

把"顺手位救了你"与 NPC 连起来：某件突发事件化解之后，**下一次敲门时对方提一句**
（"上回你家炉子灭了我还以为你要来借火"）。这需要 `run` 上记一个"最近化解过哪类事件"，
而 `eventHistory` 那套已经有形状（`recordEvent`）。⚠ 它是**加分项**，
做不成不影响 ①②。

**它依赖的东西**：⛔ 无（不像原来那样依赖决策 D 的"要不要进 quality"）。
★ 而原解法 ②（进 `quality`）**降级**为可选项 —— 用户没有要求改数值，
而它会让三条永久回归探针的基线漂 —— **不做**。

#### 这一组要用户拍板的点（收敛成两个）

1. **回报 B 的形态**（少数事件化解后"对方留下点东西"）：现金 / 一小箱 / 情报 —— 哪几种？
2. **剧情那条做不做**（它是加分项，需要记"最近化解过什么"）。

（原"要不要进 `quality`"这一问**已由用户的口径回答**：重点是显眼与回报，
不是改数值 —— 所以**不做**，探针基线不动。）

### 决策 E：任何东西都**不要容易被忽略** —— ✅ **已拍板（2026-10 用户）**

**用户的口径（原话）**：

> "突发事件更明显一点，不光是突发事件，尽量任何东西都不要让用户有那种容易忽略过去的感觉，
>  都显眼一点"

★ 这条**比决策 D 大得多** —— D 是"顺手位相关的事件"，E 是**一整套界面纪律**。
而它正好是 M4 目标 4（"整理的反馈要更细"）与目标 3（"成果要能被反复看见"）的合流。

**从"容易被忽略"的角度盘一遍**（按严重度排，每一项都是实测过的事实）：

| # | 什么地方容易被忽略 | 现状（证据） | 改法 |
| --- | --- | --- | --- |
| 1 | **生存期日报里的"事件"** | 事件只占 `run.log` 里的一行，与"消耗 主食 2"那种流水混在一起 | 日报里**单独一块**（像"今天"那块），并带它的正文与后果 |
| 2 | **突发事件"化解了"** | 化解 = 什么都没发生 → 读起来像"今天挺平静" | 决策 D 的 ④（说出本来会发生什么） |
| 3 | **"顺手位"是否生效** | 它**不进 `quality`**，所以每天那 9 / 18 / 27 点体力里**读不出它** | 日报加一格"**随手够得到 N 天**"（= W-08 那条） |
| 4 | **情报（D-13）** | 它只在生存期日报的一块里，而它的价值是跨局的 | 结算页也要报；下一局开局要能看到 |
| 5 | **胶带上的小墨点**（"它不在这张胶带的清单里"） | 刻意的**中性**（§5"游戏不评判对错"）—— 但中性≠看不见 | ⚠ 它与 §5 有张力：**这条要小心**。建议只提高对比度，不改成朱红 |
| 6 | **成就解锁的瞬间** | 现在只有 `CodexScreen` 里的一枚印章 | 解锁时给一个**当屏**的提示（音效 `playSfx` 已有） |
| 7 | **"整整齐齐"徽章** | 只在结算页的 `tidyShelfIds` 里出现 | 整理页当场给反馈（`isShelfTidy` 是现成判定） |
| 8 | **新内容（60 条突发见 7%）** | 一局只见 7% 的事件池 | 决策 E-出现率：0.3 → 0.45（**要拍板**，见下） |

★ **这一条的建议做法**：**不要一次全做**。先做 1 / 2 / 3 三项（都在生存期日报那一屏，
而且它们互相关联：事件显眼 + 后果可见 + 顺手位可读），然后再盘剩下的。
**理由是**：这 8 项里有 3 项（5 / 6 / 7）会碰到 §5 的"不评判"边界，
而那需要一条一条想，不适合打包做。

#### 这一条要用户拍板的点（一个）

**突发事件的出现率**：`EMERGENCY_CHANCE` 0.3 → 0.45（14 天碰到 4.2 → 6.3 次，
一局能见到 7% → 11%）？

⚠ 它改的是"稀而重"还是"常见而轻"的手感，而 `data/emergencies.ts` 的注释明确写过
"它要像意外，不能像日程"。★ 而且这个常数**有过前科**：它原来按"7 条事件"反推，
M3 加到 28 条时同一个常数让概率变成 **63%**（纪律 §3.10 就是那次）。
★ 我的建议：**先不改出现率**，先把"显眼"做掉（表格 1~3）——
因为"见过 4 次却没印象"与"见过 6 次却没印象"是同一个问题，
而**显眼**不需要动内容量。

### 第二组：把"数值轴"接成"位置轴"（M4 的正题）

#### W-05 ★★★ 让事件从"加减数字"变成"改盘面"

169 个事件里 **104 个**会往家里加货、**65 个**只动四维与现金，
而**没有一个**改变已有物资的归属。真正会动货架的只有 `model/scatter.ts`（同一行内、不碰胶带）。

两个具体口子：

- **`stockCut` 只削商店、不碰玩家家里**（而且 169 个事件里 **0 处使用**）。
  补一个**会打到玩家家里**的效果，例如"楼下车库进水，最下面那一排泡了" ——
  `setup.ts` 的注释早写好了那个叙事（"进水/结冰/塌方都是**从下往上**吃掉空间"），
  只是从来没兑现过。**它让哪个决定不同**：**"低处放什么"**第一次成为可后悔的决定；
- **加一类新效果** `relocate` / `zoneBreak`（打散某一行 / 撕掉某一行胶带）。
  **它让哪个决定不同**：玩家会开始问"**哪一行即使被撕掉胶带我也不心疼**" ——
  这个决定**现在完全不存在**，因为胶带永远安全。

#### W-06 ★★ 给 1~2 个身份一条整理向的天赋

10 个身份的天赋**全是** `categoryDiscount`（唯一执行点 `systems/shop.ts`），
而 `data/identities.ts` 自己写着"失衡红线：只要『囤什么都行』成立，整理就失去意义"——
现状是**所有身份都在改"囤什么划算"，没有一个改"整理划不划算"**。

- **改法**：扩 `PerkRule` 加一个成员（例如 `{ kind: 'workCostFactor'; rate: 0.8 }` 装卸工、
  或 `{ kind: 'extraHandySlot' }` 小区保安）。`workCostOf` 的读点**只有 2 处**，接线面很小；
- ⚠ **不要加进熟练度等级**：`systems/identity.ts` 明写"等级**只改开局条件、不改单局中的任何公式**"，
  而那条约束是**为了三条永久回归探针**立的 —— 动它要一并处理探针口径。

#### W-07 ★★ 家具：拆掉两个"没有取舍的决定"

**① 冰箱严格支配另外两种**：冰箱 0.4 / 柜子 0.75 / 货架 1.0，而三者**同价（100）同格（24）**。
而 `data/furniture.ts` 那句 `why` 写的"装鲜食能多撑一阵，**装别的占地方**"——
那个代价**在代码里不存在**。

**② 而它的期望收益可以精确地是 0**（实数）：记 `D = E / spoilRate`（这件货在普通货架上还能撑几天），
14 天窗口里 `5.6 < D ≤ 10.5` 才**只有冰箱救得回来**；`10.5 < D ≤ 14` 时柜子与冰箱**等价**；
`D > 14` 时货架与冰箱**等价**。**冰箱相对柜子的优势只活在一个 4.9 天宽的窗口里。**
而实机每一局都是寒潮（`spoilRate 0.5`）→ 最短鲜食在普通货架上也活得过 14 天。

**两条便宜解法**（都顺）：

- 给冰箱一个代价（`h: 3` = 18 格，或价格抬到 140）—— "买保护"与"买地方"第一次成为同一笔钱的两个用途；
- 给灾难加一个 `fridgeDead`（断电类灾难里冰箱按 1 算）——
  ★ 它**不是新发明的叙事**：`data/disaster.ts` 的 notes 已经写着"外面转暖，**室内外冷藏链同时断**"、
  "**冰箱停摆**让腐坏加速"。把已经写好的话变成机制就够了。

#### W-08 ★ 反差层：把"囤得多"和"囤得好"分开

那四格的输入**没有一个来自整理系统**（`(day, disasterId)` / `(shelter)` /
`(货架∪**纸箱**的件数, 日耗)` / `(day)`）。最要紧的一条：`supplyDays` 把**货架与纸箱加总**，
所以"把 30 罐从纸箱搬到贴好胶带的架上"在这块屏幕上**一个数都不变**；它也不读到到期日。

- **最便宜的一条接线**：加一个同源函数，件数只数"按取用顺序真的够得到的那部分"
  （极限情况就是 `countOnHandy`），在日报加一格"**随手够得到 N 天**"；
- **它让哪个决定不同**：**"搬上架 / 贴胶带 / 标顺手位"这三个动作今天在日报上完全不可见** ——
  改完会在玩家每天必看的那一屏上直接变成天数差。

### 第五组：★ 顺手位的存在感（用户 2026-10 提的问题）

> 用户的原话：
>
> > "顺手位的作用目前来看还是不够明显，因为你的那些事件我基本都没怎么见过，
> >  很那见到，需要顺手位的也很少，事件在我从你的代码里看是很多，
> >  但是出现率和存在感太低了，而且事件比如小侄女要奢侈品这种他并不会给我任何好处，
> >  顺手位有没有又怎么样呢，怎么平衡解决一下这个问题"

这一组是**四条主张**的对照实验结果。★ 其中**两条被数据推翻、三条被证实** ——
而证实的那三条指向同一个结论：**不是"要不要顺手位"，而是"玩家感觉不到它起作用"**。

#### 实测（2026-10，`EMERGENCY_CHANCE = 0.3`，生存期 14 天）

| 用户的说法 | 实测 | 判定 |
| --- | --- | --- |
| 事件很多 | **60 条**突发（medicine 9 / fuel 10 / tool 11 / warmth 7 / food 9 / water 6 / luxury 8） | ✅ 成立 |
| 出现率和存在感太低 | 每天 30% → **14 天只碰到 ~4.2 次**；一局能见到的比例 **7%** | ✅ **成立，而且是最硬的一条** |
| 需要顺手位的很少 | **60 / 60 条都需要**（`needOnHandy` 是它唯一的判据） | ❌ **不成立** |
| 小侄女要奢侈品却不给好处 | **60 条里带奖励字段的：0 条** | ✅ 成立（而且这是**刻意的**，见下） |
| "顺手位有没有又怎么样" | 它**不进 `quality`**（`quality = 归位×0.6 + 临期×0.4`）→ **不影响每天的翻找体力** | ✅ **成立** |

#### 根因（三条，都是"感觉不到"，不是"没有用"）

1. **好处是"什么都没发生"**。化解一件突发的全部回报是**避免** `lost`（扣四维）——
   没有正收益。所以玩家在屏幕上看到的是"今天挺平静"，而不是"我的顺手位救了我"。
   ⚠ 而这是**刻意的**：§5 引擎①"游戏不评判对错"要求系统不夸、不评分。
   **修法不能是"加分"，否则会变成系统在打分。** 只能是"**让本来会发生的事可见**"（见解法 ①）；
2. **它在日结的账里不参与**。`organizeQuality` 只吃 `placement` 与 `fefo`，
   所以顺手位**不影响每天那 9 / 18 / 27 点的翻找体力**（那才是玩家每天都在读的数）。
   它只在**体力 < 30 那天**硬性生效（取用 = `ceil(need×0.5)` + 顺手位件数）——
   而"体力见底"在整理得好的档里**很少发生**。于是它的作用正好在**你不需要它的时候才出现**；
3. **一局见不到几条**。4.2 次 × 每次只占一屏 —— 而 60 条内容平摊下来，
   玩家**三局才能见到同一件**。存在感低是**内容量与出现率的比值**问题。

#### 解法（★ 已按用户 2026-10 的口径收敛为「显眼 + 回报」，见决策 D）

**用户的口径**：*"重点是让跟他有关的那些事件更显眼一点，且能给我带来收益或者有趣的剧情
或者成就解锁或者全都有"*。所以原来的三条解法重排成下面四件，**按这个顺序做**。

**第一件：让事件本身显眼（用户点名的第一句）**

现状：事件只占 `run.log` 里的一行，与"消耗 主食 2"那种流水混在一起。
而 `ui/SurvivalScreen.ts` 的日报其实是**分块**的（"今天"那块 / 安全 / 四维…）——
所以改法是**把事件提成自己的一块**，带它的正文与后果，而不是夹在流水里。

```
现在：  ... 消耗 主食 2、饮水 2、燃料 2 / 夜里暖气管冻裂了，顺手位上有 3 件燃料，用上了。 / ...

改成：  ┌ 今晚出了一件事 ────────────────┐
        │ 夜里暖气管冻裂了。              │
        │ 顺手位上有 3 件燃料，用上了。    │
        │ （那一格要是空的：健康 -2）      │   ← 见第二件
        └──────────────────────────────┘
```

- **它让哪个决定不同**："我今天要不要花两分钟把药挪到门口" —— 第一次能**看见**那件事；
- **成本**：小（一处渲染 + 一个已有字段 `lost`）；
- ⚠ 不要在**没化解**时也说教（那已经是惩罚了）。

**第二件：让"本会发生的事"可见（第一件的前提）**

化解时补一句**反事实的陈述**（不是夸奖，是陈述）："（那一格要是空的，今晚要掉 2 点健康）"。
★ 它符合 §5：**陈述事实，不夸玩家**；而且它把"什么都没发生"翻译成"**本来会发生的那件事**"——
与 §6.6 反差层同一套手法。

**第三件：给回报（用户点名的第二句）**

⚠ **坑**：§5 要求系统**不夸、不评分**，所以**不能**做成"顺手位有货 → 加心情 X 点"
（那会变成计分，而且玩家会开始刷）。合口径的三种：

| 路 | 形状 | 做法 |
| --- | --- | --- |
| **A. 收益是"省下来的"** | 第二件已经做了这件事 | 文案 |
| **B. 收益是一件东西**（建议做 1~2 条） | 少数事件化解后**对方留下点东西** —— 与求援的 `thanks` 同一个机制（现金 / 一小箱 / 一条情报） | 加一个可选字段 + 1~2 条内容 |
| **C. 收益是成就**（用户点名） | 新增 2~3 条：连续 N 天不让突发事件得手 / 在顺手位备齐过全部应急品类 / 某条特定事件的后续 | 加成就（**不需要新埋点**：`emergencyHurtCount` 与 `countOnHandy` 都在跑） |

★ **建议三条都做**（用户说"或者全都有"）。

**第四件：剧情（用户点名的第三句，加分项）**

把"顺手位救了你"与 NPC 连起来：某件突发事件化解之后，**下一次敲门时对方提一句**
（"上回你家炉子灭了我还以为你要来借火"）。需要记一个"最近化解过哪类事件"，
而 `recordEvent` / `eventHistory` 那套已经有形状。⚠ 做不成不影响前三件。

**★ 而降级的两条（不做）**：

- ~~把 `emergency` 放进 `quality`~~ —— 用户的口径是"显眼与回报"，不是"改数值"；
  而它会让三条永久回归探针的基线漂。**不做**；
- ~~提高出现率~~ —— 见决策 E 的最后一段（**先做显眼，先不动内容量**）。

★★ **奢侈品那 8 条自成一个子问题**（用户的例子正是它）：
`luxury` 不参与生存数值，而 `keepsake` 承诺的"摆放回心情"**全仓零读取**（D-29）。
所以"小侄女要奢侈品"的**兑现是空的**：对她换不到东西，对你**可以拒绝**，
而拒绝的代价只是 `lost` 里那 1~2 点心情（四维里最便宜的一项，睡觉就回）。
★ 于是这 8 条**在博弈上是"永远拒绝"** —— 这不是 bug，是**没有设计的后果**。

**处置（三选一，要拍板）**：① 接线 `keepsake`（摆出来的纪念品回心情）——
那样"给她一罐可可粉"就**真的有代价**了；② 把这 8 条改成"**她要的东西对你有用**"；
③ 让其中几条化解后**给回一件东西**（第三件的路 B，那样"给"就不亏）。
⛔ ① 依赖 **W-04 里 `keepsake` 那条**。

#### 这一组的验收口径（能用断言量的）

- [ ] **每一条化解之后，日报里能读到"本来会发生什么"**（现在读不到）——
      可写成"化解与不化解两种情况下，日报都含那件事的代价陈述"；
- [ ] **事件在日报里有自己的块**（不再混在流水里）—— 可写成渲染断言；
- [ ] **至少 1 条突发事件化解后给出东西**（第三件的路 B）—— 可写成事件效果断言；
- [ ] **至少 2 条新成就与"用上顺手位"直接相关**（现在 0 条）—— 可写成成就判定断言；
- [ ] 奢侈品那 8 条：**"给"与"不给"两个选择的期望差不为零**
      （现在给 = 白给，所以是零差 —— 可用三局探针对比）；
