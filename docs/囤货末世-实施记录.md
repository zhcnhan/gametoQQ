### 7A. 实施期间对 §7 的增补（v0.3 → v0.4，都已落地）

开发过程中为**正确性**所做的模型变更，列在这里以免 §7 与代码脱节：

1. **`RunState.seed`** —— §7 遗漏了它；"一切随机走种子化 RNG，seed 存进存档"要求它存在。
2. **`boxesToUnpack: UnpackBox[]`**（原 `ItemStack[][]`）—— 用下标当箱子身份时，
   空箱被摘除会让后面所有箱子串位，"放回原处"必然放错。且采购要按箱型补货，
   必须区分"箱型"与"这一箱"。`UnpackBox = { id: string; defId: string; items: ItemStack[] }`。
3. **`DisasterProfile.spoilRate`** —— 见下方标注。这是 v0.4 的核心新增。
4. **`IdentityDef` 增 `tagline` / `carryLimit` / `perkRule`** —— §6.2 点名了「背负重」，
   但 §7 只给了 `vehicleCapacity`；而 `perk: string`（"燃料价格 -20%"）是给人读的，
   代码没法据此算折扣，必须有一份机器可读的 `perkRule`：
   `{ kind: 'none' } | { kind: 'categoryDiscount'; categories: CategoryId[]; rate: number }`。
5. **囤货期四字段 + 夜间一字段**（§6.2 的实现所需）—— 已列在上方 `RunState` 里。
6. **点位与当日库存**（§6.2 的"地图点位 + 三约束"所需）：
   `ShopDef = { id: ShopId; name; blurb; priceFactor; offers: { itemId; stockBase; stockJitter }[] }`；
   `ShopDayStock = { day: number; shopId: ShopId; lines: { itemId; price; stock }[] }`。
7. **夜间事件**（§6.2 的"夜间小事件"所需）：
   `NightEventDef = { id; text; options: NightOption[] }`；
   `NightOption = { label; outcome; effect: NightEffect }`；
   `NightEffect = { cash?; health?; mood?; stamina?; shelter?; boxDefId? }`。
8. **`Zone.autoAccept` 的落地形态**：从"可选自动接收规则"收敛为**品类清单**
   （`{ categories: CategoryId[] }`），`tags` 分支暂时不用 —— 7 个品类在手机竖屏上
   刚好排成 4 + 3。空清单 = 什么都收。

> **[进度 D-03 · 挂起]** `spoilRate` 表达的是本案的一条立场：**腐坏是灾难的属性，不是物资的属性**。
> `1` = 真实保质期；`> 1` = 加速（热浪 / 洪水 / 疫情，会让粮仓变成坟场）；
> `< 1` = 延长（寒潮 = 天然冷库）。**寒潮取 0.5（已拍板），于是 M1 全程不会发生腐坏** ——
> 引擎④「FEFO = 零腐坏」、冰箱、§6.4 的损耗行在 M1 里都是装饰。
> 推进算法约定：`day < 0` 按真实天数；`day ≥ 0` 按 `virtualDay = day × spoilRate` ——
> 囤货期买的货按真实保质期计，灾难一来才开始被以另一种速度吃掉。
> 该字段在代码里是**必填**的：将来加第 2 个灾难时，忘记想"这场怎么处理腐坏"会直接编译不过。
>
> **[进度 D-07 · 已清偿（2026-10）]** 原来那句话是"`ItemDef.slotSize` 没有参与任何计算
> （槽位矩阵实际是"一格一栈"，大米和电池占同样一格）。要么让它真的吃格子，要么从 §7 里删掉它
> —— 悬着最差。" **选了删**：它在代码里零读者、界面里零渲染、策划案里只出现在那个类型块。
> 详细理由见 `src/meta/deferred.ts` 的 D-07。
>
> ★ **"让它真的吃格子"没有丢**，它登记的正是下面这条候补 —— 而归 §10.1A 的第 1 条
> （"整理本身要有更多决定"）。

## 10. 开发路线图

> **[修订 · M2 范围调整（v0.8）]** 原 M2 那一行混了三种性质完全不同的工作，M2 开工时拆成两条轨：
>
> | 轨 | 内容 | 验收口径 |
> | --- | --- | --- |
> | **M2 · 玩法轨**（代码） | 突发事件、白天随机事件、图鉴 + meta 闭环、归位率修复、安全感快照、luxury 品类 | 代码验收：探针、种子化测试、tsc/build、320/375/390 零溢出 |
> | **M2 并行 · 美术轨**（设计师） | 窗口反差渲染、拟声字手写 SVG、淡彩图标、整理 ASMR 音效 | **不作为 M2 代码验收项**；代码侧只留挂载点 |
>
> 拆开的理由很直接：原 M2 把"爽感打磨"与"设计师出图"混在一个里程碑里，
> 于是代码侧的验收标准无法判断它到底做完了没有。**云备份从 M2 挪到 M2 收尾或 M3** ——
> 它是零玩家可见价值的工程项，混在爽感里程碑里必然挤占爽感项。

| 里程碑               | 内容                                    | 验收标准                        |
| ----------------- | ------------------------------------- | --------------------------- |
| **M0 手感原型**（约1周）  | 仅整理界面：拆箱→拖拽上架→吸附→分区命名→保质期排序→FEFO 模拟消耗 | 不看教程能玩 10 分钟不腻；放置音效"上瘾测试"通过 |
| **M1 单局闭环**（1~2周） | 先知日历+扫货+夜间事件+生存期每日结算+3 个求援订单+结算评分     | 完整跑通一局（7+14 天），存档/读档正常       |
| **M2 爽感与闭环**（玩法轨） | ①突发事件 ②白天随机事件 ③图鉴+meta闭环 ④归位率修复 ⑤安全感快照 ⑥luxury 品类 | 三条全周期探针成立；新增事件有种子化测试；320/375/390 零溢出；tsc/build 干净；策划案与 deferred 零偏差 |
| **M2 并行 · 美术轨**（设计师） | 窗口反差渲染 / 拟声字手写 SVG / 淡彩图标 / 整理 ASMR 音效 | 不进代码验收；代码侧挂载点已留 |

| **后续**            | 小程序移植评估 / 云备份（从 M2 挪来）/ 分享晒图          | 视数据决定                       |

> 完全不跟手、中心放不准），根因共 **6 条**，全部定位并修复：交换的中间状态建模错误、

> `.drag-ghost` 缺 `pointer-events: none`。**这一轮同时补上了缺失的验证手段**
> （`ui/fakeDom.ts` 假 DOM + `__tunhuoTrace` 运行期诊断 + 屏幕级测试 `ui/swapDrop.test.ts`）。
> 完整教训记在 `docs/囤货末世-开发纪律.md` §2。
>
> **一条流程教训，值得写进本案**：这批 bug **一个都不是靠读代码发现的** ——
> 全部来自"能复现的测试"或"运行期诊断输出"。而在此之前我连续猜了 7 轮。
> **§验收那条"改数值必须先跑探针"的规矩，适用范围应当扩大到所有交互逻辑。**

**给 code AI 的开发提示**：

- 先做 `model/` + `data/` 并可单测，再接 UI；状态机驱动一切界面切换
- 拖拽用 Pointer Events 自己实现（不用 HTML5 DnD，移动端兼容性差）
- 所有随机（商店库存/事件/批次保质期）走种子化 RNG，方便存档一致与调试
- 存档 schema 从第一天带 `version` 字段
- ★ **新增内容一律先在 `data/` 加一条**（事件 / 物资 / 订单），逻辑层不许出现 if 分支的硬编码名字。
  M2 的突发事件、白天事件、奢侈品都是照这条走的：加内容 = 加一行数据，不动代码

## 10A. 候补清单（M3 及以后集中登记）

> 这一节是 M1/M2 评审产出的、**明确不属于当前里程碑**的建议。集中登记在这里，
> 是为了避免它们散落在聊天记录与代码注释里 —— 散落 = 三个后月没人知道曾经想过这件事。
>
> 判定它们"去哪儿"的规矩：
> 新设计决定 → §12 加拍板条目；新技术债 → `src/meta/deferred.ts` 登记（D-xx）；
> 里程碑范围调整 → 修订 §10；**还没到能拍板程度的想法 → 就写在这一节**。

1. **NPC 囤货期露脸（人格化的前后呼应）**
   D-5 王阿姨在楼下嘲笑"囤盐有什么用"，D+8 她来敲门 —— 同一件事的两端。
   现在 NPC 只在生存期出现（敲门的三种订单），囤货期一个人都没有。
   留着它的理由：这是全案唯一一处能"零台词"讲完一个故事的机会（§6.6 的克制纪律同样适用）。
2. **每日日报一键成图分享卡片**（从原 M2 条款升级为 M3 传播专项）
   黑白手账版式 + 朱红印章（"已囤 47 天"）。它与「小程序抢滩」的触发条件绑定：
   先在 H5 上验证"晒"这件事有没有人做，再决定要不要为它做小程序那套分享链路。
   **"晒"是本品类的核心玩法**（§2：链接即传播），所以它不是锦上添花。
3. **新手引导（第一局用"一张贴好的胶带"做活例）**
   看见 → 模仿 → 自建。注意与 §5「整理期完全静默」的边界：
   引导只能出现在**开局那一次**，而且必须是一条"已经贴好、写好清单"的现成胶带，
   不能是弹窗提示 —— 否则整理期就不再是禅时刻了。
4. **最简埋点定义（流失天 / 退出屏 / 整理率分布）**
   §3.1 与 §12 的"视数据决定移植"需要数据，否则是空话。
5. **★★ 物资本身的「物理大小」（一袋米占四格）** —— D-07 删除时转登记到这里
   原来 `ItemDef.slotSize`（1=小件 / 2=大瓶 / 4=整袋）就是为它留的位子，
   而它**从来没有生效**（大米和电池占同样一格），所以 2026-10 把它删了
   （见 D-07 的清偿记录）。**方向本身没丢，只是它不属于 M3。**
   它值得做，因为它直接加厚 §10.1A 的第 1 条（"整理本身要有更多决定"）：
   "一袋米占掉四格，值不值"是一个**现在不存在**的取舍 ——
   而它恰好是本作的核心动作（把东西塞进有限的空间）。
   ⚠ 代价要提前说清：它同时动**放置 / 合并 / 拖动 / 容量 / 存档**五处，
   而且"一格一栈"这个前提一旦松动，`slotSize` 会在**全表 121 件**上
   重新变成平衡问题（谁该占 4 格、价格要不要跟着改）。
   所以它是一次**机制级**改动，不是给一个字段接线。
6. **囤货期的「访客来源」**（D-13 清偿时发现的缺口）
   情报做出来了，而它**只从求援订单来** —— 求援是生存期的事（§6.5）。
   于是情报天然来得晚，而它最大的用处（排采购、决定先囤什么）
   在**囤货那 7 天**。现在它的价值是**跨局**的（这一局挣到的，下一局开局就知道更多），
   那有一点元进程的味道，但**不构成本局的一个决定**。
   要做的是：囤货期也能碰上"有人带来消息"的场合 —— 一个上门的人、
   一条业主群里的传言、或者那台 `radio_set`（它现在 `nutrition: {comfort: 1}`，
   只有"心情"这一个作用，而它的文案写的是"换来「知道外面怎么了」"）。
   ⚠ 与候补第 1 条（NPC 囤货期露脸）是同一片区域，可以一起做。
   三条够用：**她在第几天不玩了**、**在哪一屏关掉**、**整理率通常落在哪一档**。
5. **无障碍：警告不独靠朱红色相（加形状）+ 左手镜像热区**
   现在是"朱红 = 警告"单一通道；色觉障碍玩家读不到那一层。
   加一个形状（三角/斜线）就能解决，而热区镜像对单手左手用户是硬需求。
6. **结局"最后一页"演出（低成本高情绪）**
   死局：撕掉的日历；生还：翻过来的春天。都是纯 CSS + 已有的纸纹基底，
   不需要新美术资源 —— 属于"美术轨之外、但代码侧能做"的那一类。
7. **奢侈品扩展与回收**（与 D-16 一起）
   现在 5 件奢侈品只进图鉴与心情。M3 可以给它们一个出口（换东西 / 送人 / 摆出来看），
   否则它们的"价值只有两条"会显得单薄。
8. **新身份与天赋等级**（§6.7 的"身份等级"一半没做）
   `MetaProfile.identityLevels` 已在类型里预留、M2 的存档也带着它，但**没有任何东西写它**。
   这是一笔已经付了类型成本的欠账，别让它烂在那儿。

### M3-1 让 AI 批量生成内容（并保证生成物合格）

这是用户明确要的能力："数百种事件由 AI 直接生成，或给提示词去问更高级的 AI"。
**可行的前提是"生成物能被机器判合格"** —— 否则人会淹没在校对里。

流水线（每一环都要有工具，缺一环这条线就不成立）：

```
① 起草提示词（人写一次，之后复用）      → 见 §10.2.7 附
② AI 批量产出（只出数据，不出代码）
③ scripts/check-content.mjs 静态校验    → id 重复 / 字段缺失 / 引用悬空 / 数值离群
④ 语义校验（已有测试直接复用）           → 「每个选项都得有真实收获」那条 M2 规则
⑤ 探针（好档 / 乱档 / 补救）             → 数值没有漂移
⑥ 人工过一遍文案                         → 只改字，不改结构
```

**给"生成事件"的提示词必须包含**（这几条是 M2 的教训换来的）：

- 输出**只有数据**，严格符合给定 TypeScript 结构，**不许写解释、不许写代码**；
- **文案纪律**（§5A 与 M2 的结论）：天气只报温度不拟人、环境不许有"记性"
  （"上次的事人家还记得"这类一律不许）、正文不用破折号、1~2 句、选项 ≤3；
- **每个选项必须有落到玩家身上的真实效果**，且**文案承诺什么就必须给什么**
  （M2 抓到过"文案说结完账了，效果里根本没有结账"）；
- **同批不许重复同一个取舍**（见 §10.2.6）；

#### M3-2.2 第 3 步的口径（身份熟练度 + 分批）

**熟练度（§10.2.3）**

| 项 | 定下的口径 |
| --- | --- |
| 升级条件 | **用同一身份活到最后一天**（`outcome === 'survived'`）。倒下的那一局不算 |
| 等级 | 1~3。**没记录 = 1 级**（不是 0）—— 一个从没活到最后的身份也是能用的 |
| 每级加成 | 开局现金 **+40** / 车载 **+3kg** / 单趟 **+1kg**（约基准值的 4~5%） |
| 生效范围 | **只改开局参数**。单局中的任何公式都不读等级 |

★ **加成为什么这么小**（这条决定值得写下来）：§6.2 的三约束本身是紧的 ——
两个身份的开局现金 780~1150，而 14 天刚需约 700~810，余裕只有一成上下。
一个"每级 +10%"的加成就足以把「要不要少买两罐燃料」这个决定抹平，
而那是寒潮局唯一的核心取舍。所以加成的目标是**让同一个身份的第二次稍微松一点**，
不是碾压。测试里把"小"写成了可执行判据：满级总加成 ≤ 基准的 15%。

★ **等级做成 `RunState` 上的快照**（`identityLevel`），不在每次读的时候去 `meta` 现算。
两个理由：① 命令层（`buildCartView`）手里只有 `run`，而界面层手边有 store ——
现算会让两边算出不同的数（"界面说一趟能拿 19kg、实际 18kg"，本项目在限购那处吃过同一个亏）；
② 现算意味着等级会在局中途变化（玩家通关另开一局之后回来读旧档）。

**开局分批（"三选一"，不是"九选一"）**

| tier | 身份 | 为什么在这一档 |
| --- | --- | --- |
| **1（开局）** | 社区团购团长 / 加油站夜班员 / 夜班护士 | 定位最直白：钱多 vs 车大 vs 药便宜 |
| **2** | 外卖骑手 / 小区保安 / 裁缝 | 要先玩过一局才看得懂（偏门品类折扣；"什么都会一点"要先知道三约束） |
| **3** | 退休教师 / 装卸工 | 极端定位，好玩恰恰因为**玩家已经知道正常玩法是什么样** |

★ 这是**内容分层，不是强度分层**。测试里有一条逐对比较，抓"高 tier 全面强于低 tier"——
那等于"解锁一个更强的选择"，是数值成长而不是新打法，与 §10.2.3 的红线冲突。

未解锁的身份**仍然列在开局页上**（只给名字与解锁条件、不给数值）——
与图鉴那条同一个道理：不列出来，玩家就永远不知道还有别的身份可玩，
而"下一次换个身份再来"正是 §10.2.1 说的重开动机。

#### M3-2.3 文案口径的一条修订（用户看过界面之后定的）

用户的原话：**"不要用撑满，硬抗，这种词，任何地方都不要，太尬了"**。据此定的口径：

| 原来的说法 | 改成 | 场景 |
| --- | --- | --- |
| 撑满 14 天 | **活过 14 天** | 天数明确时（成就判据、探针说明） |
| 撑满全期 | **活到最后一天** | 说的是全期 |
| 撑满 / 硬扛 | **走完** / **硬撑** | 其余；"硬扛"统一到游戏里已有的状态名「硬撑」 |

★ **两处刻意不改**：引号里的**玩家原话**（`deferred.ts` 与 `data/survival.ts` 里
"一直点过一天就能撑满 7 天"）——那是历史记录，改它等于篡改别人当时说的话。

⚠ 顺带留一个待定项：「硬撑」本身也是那一族的词，但它是**已有的状态名**
（`data/survival.ts` 的三档叫「硬撑」/「撑不住」/「快垮了」，结算页有一格写「硬撑过 N 天」）。
换它要连界面文案一起改，属于设计决定，等用户定。

**三条与原文口径的差异（都是落地时才发现必须改的，记在这里免得被当成走样）**

1. **"仓库管理员：单局上架 300 件"改成了"生涯累计 300 件"**。
   一屋 72 格，单局上架 300 件在当前空间下**做不到**，而 §10.2.4 的"更大的家"还没做 ——
   写成单局等于挂一个当前内容下永远拿不到的成就（就是 D-16 那一类错误）。
   描述里已经写明"累计"两个字。
2. **"先见之明：在 D-7 就买下"里的时间条件没有实现**。
   "第几天买的什么"需要逐局流水，而 §10.2.2 的纪律① 把埋点增量卡得很死。
   好在**囤货期一结束就再也没有采购这条路**，所以"买过"天然就是"灾难来之前买的" ——
   这个条件不需要记，它由设计保证。
3. **"就是不认输：倒下三次，第四次站住"里的"三次"没有实现**（同上，需要逐局流水）。
   判据取的是"曾经在这一场倒在半路，现在撑满了"。
   ★ 而且是**连描述一起改的**：一个写着"三次"、实际一次就发的成就是界面在骗玩家，
   而"屏幕报一件没发生的事"在这个项目里被明令禁止过。

**实测验证（§10.2.6.1 要求的：每一批内容落地后必须重跑三条探针）**

| 探针 | 结果 |
| --- | --- |
| 好档活（全上架 + 写全清单 + FEFO + 顺手位） | ✅ 撑满 14 天（`survival.test.ts`） |
| 乱档倒（全堆纸箱） | ✅ D+10 前后倒下 |
| 中途补救有用（D+2 补救能活） | ✅ 通过 |
| 走测（真实命令 × 存档往返，16 天） | ✅ 好档撑过 16 天 |

★ 这一批内容**改动了两条频率常数**，两条都是"随内容量自己漂"的坑（详见开发纪律新条目）：
`DAY_EVENT_CHANCE`（白天事件 60%）与 `EMERGENCY_CHANCE`（突发 30%）
从"手算权重常数"改成了**概率口径**，否则加内容会静默把频率改掉
（实测：加内容后白天事件从 60% 漂到 **85.9%**、突发从 30% 漂到 **63%**）。

**为什么把 `5c` 单列**：批量生成最怕"没有样板就开始生成" ——
第一批会变成事实上的标准，而它多半是错的。先手写几场把口径立住，
再让 AI 按那个口径铺量，返工量会小一个数量级。

**`5a` 落地时的三条设计约束**（后来者改这些维度前请先读）：

1. **搬运上限与行动点必须有下限**（`Math.max(1, …)`）：再糟的天气也不该让玩家
   一件都搬不动、一天一件事都做不了 —— §4A 承诺"任何界面都得有一条能走的路"，
   给 0 不是难度，是卡住；
2. **库存允许为 0**（`Math.max(0, …)`）：那正是"断供"的表达，界面本来就会报"今天卖完了"；
3. **维度只能从 `disasterModifiersOf()` 读**。散着写 `disaster.xxx ?? 1` 的地方
   迟早会有一处写成 `?? 0`（会让整个品类凭空消失），而且那是 D-20 的同一种形状。

#### **[拍板 v0.8 · 归位率的 loophole 修复]**

**问题实测。** M1 的归位率口径是「空清单 = 什么都收」，于是 **贴一张空胶带 = 归位率恒满**。
最优解退化成"贴一张空胶带"，§5 引擎①「自建秩序」的决策乐趣被整个绕过 ——
这是引擎① 自己写的口径里长出来的漏洞，不是实现 bug。

**账怎么算。** 归位率是**三个**下游的共同输入：每日劳作成本（`workCostOf`）、
求援订单的凑单成本（`searchCost`）、应急可达率。改它 = 全数值链重对表，所以先算清两条候选：

| 候选 | 口径 | 代价 |
| --- | --- | --- |
| 甲 | 空清单胶带的堆按 **50%** 计入归位 | 保留"我不分类也是正经营法"，但 50% 是凭空约定的数，玩家无法从界面推导出来 |
| **乙（采纳）** | **只有被某张清单明确写进去的堆才算归位** | 语义一句话说完："归位率量的是你守没守自己写的秩序"；代价是"上架但没写清单"掉到 0 |

**改动。** 新增 `model/shelf.ts` 的 `zoneListedFor`（明确清单），归位率与「整整齐齐」改走它。
`zoneAccepts` 维持原义**不动** —— 它回答的是「容不容」，而它的两个读者本来就该这么读：
`consume.ts` 的取用顺序（没写清单的胶带确实把东西码整齐了，从它上面拿就是"伸手拿"）
与 `isOffZone` 的墨点（空胶带没有排除任何东西，不该被人格化成"你放错了"）。
两张判定分开写、注释里把账说清，是这次修复最容易被后人改回去的地方。

**实测验证表（`workCostOf`，件数 3 —— 求援订单"要 3 件药"那一档）。**
数字没变，但**中间那一档的性质变了**：

| 摆放 | 归位率 | 临期优先 | 整理质量 | 凑齐要花 |
| --- | --- | --- | --- | --- |
| 上架 + **写明清单** | 1.00 | 1.00 | 1.00 | **4.5** 点 |
| 上架，但没写清单 | 0.00 | 1.00 | 0.40 | 9.9 点 |
| 原封不动堆在纸箱里 | 0.00 | 0.00 | 0.00 | 13.5 点 |

老口径下中间那一档拿的是"胶带什么都收"的**归位率满分**；新口径下它的归位率是 0，
那 0.4 的质量**全部来自临期优先** —— 起作用的那一项从「归位」变成了「排架」。

**实测验证表（每日劳作，件数 6：主食 2 / 饮水 2 / 燃料 2）。**

| 摆放 | 整理质量 | 每天劳作 | 睡一觉 +12 的净额 |
| --- | --- | --- | --- |
| 写明清单 + FEFO | 1.00 | 9.0 | **+3.0** |
| 上架，但没写清单 | 0.40 | 19.8 | −7.8 |
| 全堆在纸箱里 | 0.00 | 27.0 | −15.0 |

**全周期探针（14 天口粮 30/30/30 + 药 + 2 床被；已固化为永久测试）。**

| 档 | 轨迹 | 结局 |
| --- | --- | --- |
| 好档（全上架 + 写明清单 + FEFO + 标顺手位） | 体力 100 → 88，健康 100 → 70 | 撑过 14 天 |
| 同批货全堆纸箱 | 体力 70 → 55 → 40 → 23 → 4.5 → 0 | **D+10 健康归零** |
| 乱档 **D+2** 全部上架 + 写清单 + FEFO | 体力止跌回升 | 撑过 14 天 |
| 乱档 **D+5** 才补救 | 只把 D+5 多省下 1.5 点 | **照样 D+10 倒下** |

★ 最后两行是这次重跑最有价值的一条：**逆转口的窗口是有限的**。
§12.3 v0.5 那句「代价都可逆、都能爬回来」要补一个前提 ——
体力一旦穿底，"翻不动 → 少拿 → 缺货扣健康"那一段就启动了，
此后补救只能止血、不能回天。账从体力转成了健康。

**★ 一条必须让接手者看见的后果（本方案已知的代价，不是事故）：**
空清单不给分之后，**一张清单都不写的屋子，归位率永远是 0**（心情 −4/天）。
14 天下来心情会被压到硬撑线以下，体力每天比写明清单的档多花 10.8 点 —— 大概率撑不到 D+14。
也就是说，修复之后**「不写清单」不再是一条能通关的活法**，而 §5 引擎① 那句
「不整理也能活」原本是罩着它的。两者的边界要说准：
- **仍然成立的**：不上架、不分类、把东西全堆在纸箱里 —— 也能活（纸箱可以吃，
  体力见底也还剩一半取用），只是活得难看；
- **被这一版收走的**：在整理期**一个决定都不做**（连一张清单都不写）也能通关。
  门槛其实很低（写一张"口粮区"的胶带就够），但它确实从"没有代价"变成了"有代价"。
- 若设计师希望把这条门槛再压低，旋钮有三个（按代价从低到高）：
  ① `moodFromPlacement` 的 −4 那一档；② `QUALITY_PLACEMENT_WEIGHT` 的 0.6；
  ③ 回到候选甲。**不要**去动 `workCostOf` 的两端（1.5 / 4.5）—— 那是整理"值不值得"的主轴。
