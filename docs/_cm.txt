## 这一条的根因不是"忘了接"，是"没地方接"

`Shelf.kind` 从 M1 起就存在，但只被文案读（"冰箱 C"、"放回 冰箱 原位"），
§8 写的「冰箱 1 个（腐坏减速）」一直没落地。登记的清偿条件是"M3 的多灾难"，
而那个条件**早就满足了**（116 场，八十多场 `spoilRate > 1`）。

真正的拦路石是架构：`spoilEverything` 收的是**一个全局标量 `vDay`**，
而它由"灾难的 spoilRate"算出 —— 于是"这一件放在冰箱里还是纸箱里"
**在架构上就问不出来**。所以这不是接一根线的事。

## 改法

- 新增 `data/furniture.ts`：四种家具（货架 / 冰箱 / 柜子 / 地面）各带
  `spoilFactor`、尺寸、以及**"它凭什么值得占一块地方"**那句话（界面要显示）；
- `spoilEverything(shelves, boxes, day, disasterSpoilRate)`：
  **每个容器各算各的虚拟天** ——
  `vDay = virtualDay(day, 灾难.spoilRate × 家具.spoilFactor)`，
  纸箱固定按灾难本身的倍率（"纸箱不是冰箱"这句话在代码里就是这个 1）；
- `FurnitureKind` 类型收进 `model/types.ts`（`data/` 表要 import 它，反过来不行）。

## 三处刻意的界线

1. **家具只减缓腐坏**，`spoilFactor` 一律 ≤ 1，下限 0.4。
   下限不是随手取的：再低就会出现"囤一堆鲜肉放进冰箱，整个生存期不用管"，
   而那会让**临期优先**（§6.3 三个维度之一）在装上冰箱后失效 ——
   那正是本作的核心；
2. **"让它坏得更快"是灾难的职责**，不是家具的。两者不混，所以
   `spoilFactorOf()` 里不许读 `disasterId`；
3. **寒潮里冰箱是零收益，不是负收益**，而且这是设计：全屋本来就是冷库。
   一条家具的价值随灾难变，正是 §10.2.4 说的"同一个整理动作、新的策略维度"。

## 账目

- **D-02 清偿**（冰箱没有玩法效果）；
- **D-03 清偿**（寒潮 spoilRate 0.5 → 全程无腐坏）：清偿条件就是"多灾难落地"，
  116 场里有八十多场 `spoilRate > 1`（霉雨 3.0 / 森林虫灾 2.6 / 热浪 2.4……）；
- **D-01 移除**：腐坏机制早在 M1 阶段 C 就实现了，登记册一直挂着一条 done 的账。

★ 两条"已拍板的设计决定"用例跟着改了口径，而不是删掉 ——
它们守的是不变量，账清偿之后那些不变量**仍然要守**：

- 「寒潮 `spoilRate` 必须还是 0.5」原样保留（字面量钉子）；
- D-03 那条改成查"清偿说明里写清了当初卡在哪（多灾难）"——
  防的是三个月后有人看到一条 done 的欠账，以为它本来就是小事；
- D-02 那条改成查"清偿说明里写了'寒潮里收益是 0，那是设计'"——
  防的是"既然冰箱有用，那寒潮里也该有用吧"然后去调高寒潮 spoilRate。

## 新增 `model/spoil.test.ts`（20 条，此前一本都没有）

它以前被 `survival.test.ts` 顺带覆盖（那些测的是"结算会不会坏东西"），
而那够用 —— 直到冰箱要有效果为止：**冰箱的全部意义是一条比值断言**
（同一批货，冰箱里比纸箱里晚坏），而"会不会坏东西"那种断言**永远抓不到它**。
一个把 `spoilFactorOf` 整个删掉的实现照样能让那些用例全绿。

所以这里守的是：三档在同一天同时比出来的**名次随到期日变化**（说明保护是连续的、
玩家要为"哪些东西值得占冰箱那一格"取舍）、"不改批次"这条性质
（搬进搬出不留脏状态）、以及纸箱永远等于灾难本身的倍率。
