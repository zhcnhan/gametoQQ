**8 个家族 × 若干场 ≈ 108 场**，把灾难总数从 12 补到 **112~116**。

| 家族 | 现有的 | 还要写 | 这一族的机制内核 |
| --- | --- | --- | --- |
| 温度 | 寒潮、热浪 | ~12 | 冷与热：消耗口径、腐坏方向、保暖与水 |
| 水 | 洪水 | ~14 | 有水但喝不了、低处没了、潮湿 |
| 结构 | 地震 | ~14 | 地方没了、修不完、通行受限 |
| 生物 | 霉雨 | ~14 | 东西留不住（霉、虫、菌） |
| 社会 | 骚乱 | ~14 | 门开不开不由你说了算、人来得更勤 |
| 空气 | 沙暴 | ~14 | 呼吸：待在屋里也在耗你 |
| 组合 | 大停电 | ~14 | 两三条轴同时上（最难的放这一族） |

## 1. 输出格式

一个 JSON 对象，一批一个文件，命名照 `disaster-XX.json`：

```json
{
  "kind": "disaster",
  "batch": "disaster-02",
  "batchNote": "本批 5 场，家族=水。各场主打维度与一句话选题理由。最弱的一场是哪场、为什么（这句别省）。",
  "entries": [ /* 每场一个对象，字段见下 */ ]
}
```

### 字段规则表

| 字段 | 规则 |
| --- | --- |
| `id` | 小写 + 下划线，不与现有 8 场重复（`cold_snap` / `heat_wave` / `flood_urban` / `blackout_winter` / `riot_curfew` / `sandstorm_air` / `earthquake_structure` / `mold_rain`） |
| `name` | 中文 2~4 字（"骚乱""沙暴"✅ / "城市骚乱事件"❌） |
| `family` | 上表那 8 个之一，**逐字一致** |
| `level` | `L1`/`L2`/`L3`/`L4`。**必须与真正用到的维度数对得上**（L1 ≥4 / L2 ≥6 / L3 ≥10 / L4 ≥15），校验器会逐场核对 |
| `tier` | 1=开局就有 / 2=活过一场后 / 3=活过三场后 / 4=更难。**只有寒潮是 tier 1**，你写的一律 2~4 |
| `axis` | 一句话说清**这一场哪条线在吃紧**。不许写"更冷""更难" |
| `temperatures` | 逐日外界温度（°C）。**至少给这 8 个 key**：-7/-4/-1/0/3/7/11/14（缺的日子按最近的取） |
| `spoilRate` | 1 = 真实。>1 烂得快（热、潮），<1 放得住（冷）。**区间 0.3~4** |
| `dailyDrain` | 每日额外消耗（件/天），按品类。**只写这一场特有的**（基础主食 2 / 水 2 已经内置） |
| `priorityCategories` | 2~3 个品类，这一场最刚需的。**必须和别的场次不一样**（那是"换皮"最容易露馅的地方） |
| `windowScene` | 窗外渲染主题 key，小写加连字符。可以新造（引擎按名字取景） |
| `shelterDecayPerDay` | 负数，-0.5 ~ -4。屋子每天额外坏多少 |
| `restEfficiency` | 0.4 ~ 1。睡觉回体力的乘数 |
| `carryFactor` | 0.5 ~ 1。**只能 ≤1**（一趟能提多少的乘数，天气差不该让人更能扛） |
| `actionPointDelta` | -1 / 0（**只能是这两个**，给 +1 等于发奖励） |
| `shopSupplyFactor` | 0.4 ~ 1。**只能 ≤1** |
| `closedShopIds` | 关掉的点位 id，从这 9 个里选：`supermarket` / `pharmacy` / `hardware` / `market` / `wholesale` / `community_store` / `clinic` / `gas_station` / `weekend_flea`。最多关 3 家 |
| `priceSurcharge` | 0 ~ 0.8（0.4 = 本来就贵四成） |
| `eventPoolWeights` | `{ 标签: 倍数 }`，倍数 1~4。**可用的标签只有 §3 那 7 个** |
| `npcVisitFactor` | 0 ~ 1.5。**>1 = 人来得更勤**（骚乱那种），<1 = 没人来 |
| `categoryEfficiency` | `{ 品类: 乘数 }`，乘数 **0.5~1.5**。表示"同样的东西在这一场更不管用 / 更管用" |
| `scoreWeights` | `{ placement?/fefo?/emergency?: 倍数 }`，0~10。**只在真的想换评分口径时才写** |
| `healthRiskPerDay` | **0~3**。不看玩家做了什么就每天扣的健康。**用之前想清楚**：3 × 14 天 = 42 点，那已经是"整局都在漏血"了 |
| `capacityFactor` | 0.5 ~ 1。**只能 ≤1**（屋子小一圈；"变大"是奖励，灾难不发奖励） |
| `unusableShelfIds` | 整块家具没了，取值只能是 `shelf_a` / `shelf_b` / `shelf_c`。**最多摘 1 块** |
| `calendar` | **必须 22 条**（day -7 到 14）。`severity` 0~1 且**逐日大体上升**（不要忽高忽低地抖）；囤货期那 7 天（-7~-1）severity 通常 0~0.7 之间 |
| `counterIntuitive` | ★★ **必填，而且不许糊弄**。见 §2 |
| `decisions` | 2~4 条，每条说清"它逼玩家做什么决定"。**互相不许重复**（同一个决定写两遍 = 这一场其实只有一条） |
| `notes` | 写明**用到了哪几个维度编号**、为什么这么取、以及"为什么不与已有那几场撞" |

## 2. ★★ 这一批最重要的两条要求

### ① `counterIntuitive`：这一场那条"反直觉的侧面"

它不是"再夸一句这一场很惨"。它是**一个没人会立刻想到、但想通之后觉得"确实如此"的效果**。
对标尺：

| ✅ 好的（真反直觉） | ❌ 坏的（能从"这场很糟"直接推出来） |
| --- | --- |
| 寒潮：越冷的东西越不容易坏，所以"多囤"在这一场是赔钱 | 寒潮：很冷，所以要多买燃料 |
| 热浪：夜里比白天好过，活动该挪到晚上 | 热浪：很热，所以要买水 |
| 沙暴：最难受的地方是**屋里**，封了窗细沙照样进来 | 沙暴：空气差，所以要戴口罩 |
| 地震：损失不是东西没了，是**地方**没了 | 地震：房子坏了，所以要修 |

**判据**：把那句话读给一个没玩过的人听，他如果说"哦，那挺合理的"→ 合格；
如果他说"废话"→ 退回去重想。

### ② 每场至少动 6 个维度，且**不许只在前 4 维上做区分**

前 4 维是**每日消耗 / 腐坏速度 / 刚需排序 / 外界温度**。只改这四个，
一百场会写成"十二种灾难 × 八种数字"—— 那正是这一章要避免的"换皮"。

**机器会查这一条**：任意两场如果**只在第 1~4 维上不同**，判定为换皮、整批退回。
所以每一场都要在 5~17 维里真的动几个。

进维度清单（写 `notes` 时照抄编号）：

```
 1 每日消耗 dailyDrain          10 物价加成 priceSurcharge
 2 腐坏速度 spoilRate           11 事件池权重 eventPoolWeights
 3 刚需排序 priorityCategories  12 NPC 行为 npcVisitFactor
 4 外界温度 temperatures        13 品类效率 categoryEfficiency
 5 庇护所衰减 shelterDecayPerDay 14 空间限制 capacityFactor / unusableShelfIds
 6 休息效率 restEfficiency      15 健康风险 healthRiskPerDay
 7 搬运惩罚 carryFactor         16 分数口径 scoreWeights
 8 行动点修正 actionPointDelta  17 独有机制 specialMechanics（L4 才用）
 9 商店供应 shopSupplyFactor / closedShopIds
```

`level` 的对照：L1 = 只有 1~4 维（≥4 个）；L2 = 加上 5~12 维（≥6 个）；
L3 = 再加上 13~16 维（≥10 个）；L4 = 用 17 维（≥15 个）。
**建议大批量写 L2 与 L3**，L4 留给最后那 12 场极端的。

## 3. 文案纪律（会被 `check-content.mjs` 拦）

`hint` 与 `axis` 都按这套写：

| 禁止 | 正确 |
| --- | --- |
| 破折号 `——` | 用句号断句 |
| 拟人（"风在哭""墙在呻吟"） | 只报事实："-27°C。水管冻裂了。" |
| 环境有记性（"又是这栋楼""它还记得"） | 不许 |
| 台词腔（引号对白、"某某说：…"） | 转述或直接不写人 |
| 煽情词（绝望 / 撕心裂肺 / 泪水） | 用数字表达处境："你还有 3 天" |
| 解释性括号（"（这意味着…）"） | 不许 |
| `hint` 超过 **30 字** | 1~2 句，越短越好 |

**`hint` 的写法（照着已有那 8 场对齐）**：温度 + 一个看得见的事实。
例：`"-18°C。寒潮登陆。"` / `"41°C。柏油路软了，楼道里没人开窗。"` /
`"9°C。夜里有人挨家敲门，问有没有多的吃的。"`

囤货期那 7 天（-7~-1）写"先知预告"的口气：**预言灾难要来，但还没来**。

事件池可用标签（`eventPoolWeights` 的键）—— **只认这 7 个**：

```
cold / heat / people / panic / supply / limit / market / queue
```

★ 它们来自**手写的那 4 条白天事件**（`tags: ['queue','people']` 这种）。
⚠ **生成的那 20 条白天事件一条都没写 `tags`**，所以 `water` / `neighbor` /
`dark` 这类标签目前**挂在空处**（写了也不会生效）。写 `eventPoolWeights` 时请
**只用上面那 7 个**，否则那一维是白写的 —— 而机器查不出这一点，只有这一行提醒你。
（这条账已经报给项目方，等他们补事件标签。）

## 4. 交回来会发生什么

入库前会过三道机器校验，**任何一条不合格就整批退回**（不会只退那几条）：

```bash
node scripts/check-content.mjs content/灾难/disaster-XX.json   # ① 字段/区间/引用/重复 id
npm run check:registry                                        # ② 维度签名（换皮）+ level 与维度数
npm run check                                                # ③ 全量 515 条测试 + 三条探针
```

★ 如果**只差一两条**，通常是这两种，自己先改掉再交：
- `level` 声称 L3 但只动了 8 个维度 → 要么补维度，要么如实降成 L2；
- `counterIntuitive` 写成了"废话"（从"这场很糟"直接推得出来）→ 重想。

## 5. 一次交多少

**一次一个家族，4~6 场。** 理由说清楚：口径错了返工成本与批量成正比 ——
一次 100 场全错，等于这一章要重写一遍；一次 5 场全错，改一轮就回来了。

第一批建议从**水**或**结构**开始（那两族已有的样板最完整、最容易对齐），
最后一族交**组合**（它要求同时上两三条轴，最难）。
