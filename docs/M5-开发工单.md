## 1. M5 的目标

M4 的目标是「**把每一个方面都打磨到与「物品整理」这件核心玩法相关**」——
那件事做完了。M5 的目标是另外一件，而且它同样只有一个：

> **让这一局"看起来"就是你正在经历的那一场灾难。**

这句话具体指两件事，两件都要做到才算数：

1. **视觉基调承载威胁**（现在不承载）—— 玩家在 116 场灾难里看到的是同一张米黄纸。
   用户在 D-33 里的原话是"太奶油风了，一点都不灾难"，这句是准的；
2. **先知的身份看得见**（现在看不见）—— 日历只在开局出现一次，进了囤货期就再也
   找不到了；而"我知道要发生什么"正是这个游戏的第一个爽点（§5 爽点①）。

★ 与 M4 的关系：M4 让**机制**与整理有关，M5 让**屏幕**与这一场有关。
两条轴不重叠，所以 M5 不是 M4 的续集，是另一条轴的第一轮。

## 2. 要用户拍板的两件事

★ 纪律 §6.2：**手感与视觉偏好不替用户决定**。下面两个问题都只给选项、代价与建议，
决定权在用户。**在这两件定下来之前，D-33 只做"探针先行"那一半**（见 §3 的 D-33）。

### 拍板 ①：视觉基调往哪个方向重定

现状的全部颜色都在 `src/style.css` 的 `:root` 里，而那一套是 §5A 立的：
纸底 `#f7f3ea` + 墨色 + 朱红唯一点缀 + 暖黄只给"安全 / 窗内"。
它是干净、明亮、克制的 —— 而**干净明亮克制就是"不灾难"的原因**。

| 方案 | 一句话 | 代价 | 它保住了什么 |
| --- | --- | --- | --- |
| **A. 保纸感、重定色温**（建议） | 仍是"手账"，但纸底从米白压到**阴天的灰白**、墨色加重、阴影变硬；灾难期间整页再压一档 | 要重调**全部** `:root` 变量与 `windowThemes` 的 116 组渐变 | §5A 的"印刷品质感 > 屏幕特效"这条原则；M2 立的三档边框层次只需微调 |
| **B. 黑白漫画为主场** | 把 §5A 里"反差层"的那套（暴雪=留白+速度线、高温=扭曲网点）**提到全屏**，白天也走漫画网点 | 工作量最大（网点/速度线要成为可复用的基底，不是一次性装饰）；暗底下的可读性要重新验 | 用户口味锚点里的"黑白漫画"；省美术成本 |
| **C. 灾难本身决定配色** | 页面基调跟着**这一场的灾难**走（`windowThemes` 从"窗外一条带子"升级成"整页的色温来源"） | 116 场 × 每场一套色，`check-style` 要能验"116 场没有两场撞色"；玩家换一场像换一个游戏 | 与 D-33 的另一半（先知日历）天然同源：这一场就是这一场的样子 |

**三个方案都建议保留的两条语义红线**（§5A 立的，也是这套界面**唯一**的色彩语言）：

- **朱红 = 警告**、**暖黄 = 安全 / 窗内**。换掉它们等于换一套语言，
  而 M2 花了一整轮把三档边框层次立起来、`check-style.mjs` 第 ⑧ 条守着
  "内容粗边框 ≤ 9 类"—— 重定基调时必须重新验这一条。

### 拍板 ②：先知日历上移之后说多少

用户要的三点是"**挪到最上面**、**更显眼**、**能介绍更多**"。前两点没有分歧，
第三点要定一个范围 —— 因为"能介绍更多"的上限不是数据不够，而是**会剧透**：

| 档 | 顶栏上放什么 | 剧透风险 |
| --- | --- | --- |
| **1. 只放倒计时**（最小） | "寒潮 D+3" + 一根强度条 | 无。但这与现在开局页那条灰柱子差别不大 |
| **2. 倒计时 + 这一场要什么**（建议） | 加一行"最要紧的是 主食 和 保暖"（`priorityCategories`，开局页现在就有） | 无 —— 它在开局页已经给过玩家了 |
| **3. 再加"哪几天最难"** | 加 `calendar` 里 severity 最高的那两三天的 `hint` | ⚠ **有**：`hint` 是逐日的需求暗示，本来要玩家自己从曲线里读出来。全给出去，"规划"就变成"照单执行" |
| **4. 再加"它上次怎么打倒我的"** | 跨局信息（`MetaProfile` 里要新增字段记"上一局死在第几天、缺什么"） | ⚠⚠ **最大**：它同时是玩法信息与叙事，而且这是一次 schema 变更 |

建议取 **2 + 3 的一半**：顶栏给 1 与 2，**"哪几天最难"放在点开之后的展开层里** ——
"先知要我主动去问"比"先知把答案贴在脸上"更像先知，也保住了 §6.1 那句
"日历是**规划乐趣**的来源"。

## 3. 工单

### 第一组：视觉与先知（M5 的正题）

#### ★★★ D-33 整体视觉重构 + 先知日历上移

**它让哪个决定不同**：玩家选身份、排采购、决定"先囤什么"的依据会变成**这一场**的样子；
现在他看到的是一张与灾难无关的纸。验收看 §5。

这一条**必须走两步**，而且第一步不能省：

1. **先登记新决策**。§5A 的基调是宪法级条款（`docs/囤货末世-游戏策划案.md:316`），
   改它必须先在 §12 立一条新的已拍板条目 —— 与 M4 的决策 A~E 同一个规格。
   ⚠ 这一步不做，后面所有改动都是"自己改了设计师拍板的东西"；
2. **再动手**。动手顺序建议：`style.css` 的 `:root` → 三档边框层次复验 →
   `data/windowThemes.ts` 的 116 组渐变跟着重调 → 最后才是先知日历上移。

★ **先知日历上移是一件独立的事，不要混进"把界面改好看"里**（D-33 自己写着这句话）。
它的落点是 `src/ui/PrologueScreen.ts:123-148` 现在那一块 + 一个新的常驻顶栏组件
（可以照 `src/ui/windowBand.ts` 的形状写：纯函数返回 HTML、类名带状态、
内联 CSS 变量，见那里的注释）。

**开工前先量四组数**（照纪律 §4A.2「探针先行」，改完再量一次）：

| 量什么 | 现在 | 为什么要量 |
| --- | --- | --- |
| 全部 `:root` 颜色的**明度跨度** | 待测 | "太奶油风"要能被量成"明度跨度太窄" |
| 三档边框层次的实际对比度 | 待测 | `check-style.mjs` 第 ⑧ 条守的是"类数 ≤ 9"，它**不验对比度** |
| `windowThemes` 116 组的跨度 / 饱和度 | 中位跨度 **36.7** / 饱和度 **19.5%** | M4 拉强过一次（提交 `4869848`），换基调会让这套整体偏亮 |
| 320 / 375 / 390 三档零溢出 | 320→44.8px | 顶栏塞进日历之后要重新验（决策 ② 的档位越高越挤） |

#### ★★ D-34 的遗留：结算页的"比上一局"刷新即消失

`settleRunMeta` 有幂等闸（`run.metaSettled`），第二遍返回 `null`，
于是"上一局是什么"这个**结算那一刻才有**的信息在刷新之后就没了
（`meta.lastRunScore` 本身是对的，丢的只是显示）。

要修得给 `RunState` 加一个"结算那一刻抓下来的上一局"快照字段 ——
**这是一次 schema 变更**（`SAVE_VERSION` 22）。值不值得由"玩家会不会真的刷新结算页"决定，
所以它排在 D-33 之后：D-33 会重画结算页，两件事一起做比分开做便宜。

### 第二组：机制级的两件（各要一个设计答案）

#### ⛔ 前置：W-10「一袋米占四格」—— 物资的物理大小

M4 的结论是"**不在本轮实现**"，理由是缺的不是接线，是设计答案
（见 `docs/M4-开发工单.md`「零碎收口」）。`ItemDef.slotSize` **已经整个删掉了**
（类型 / 121 条数据 / `check-content` 字段表 / `merge-content` 白名单），
`src/data/items.ts` 只留着一句注释。

它值得做，因为它直接加厚 §10.1A 第 1 条：
"一袋米占掉四格，值不值"是一个**现在不存在**的取舍，
而它恰好是本作的核心动作。**三个选项，请用户选一个**：

| 方案 | 口径 | 代价 |
| --- | --- | --- |
| **A. 只给"大类"定尺寸**（建议） | 只给米 / 水 / 燃料这类**整件**定 2 或 4 格，其余全 1 格（约 20 件要标，101 件不动） | 小：放置 / 合并 / 拖动 / 容量 / 存档五处都要动，但平衡面只有 20 件 |
| **B. 全表 121 件逐件定** | 每件都有尺寸 | 大：121 件全部回到平衡桌上，而且**价格要不要跟着改**会变成第二个问题 |
| **C. 不做** | 保留"一格一栈" | 零。核心动作少了一层厚度 |

⚠ **三条共同的前置**：它一次动**放置 / 合并 / 拖动 / 容量 / 存档**五处，
而且会推翻"一格一栈"这个前提 —— 全仓有几处代码**默认了它**
（`model/shelf.ts` 的 `getStack` / `setSlotStack`、拖动落点判定、`countInPlace`）。
选 A 或 B 之前要先做一次**接线审查**（纪律 §4A.5），把"哪些地方假设了一格一栈"数清楚。

#### ⛔ 前置：D-35 第 17 维「独有机制」

字段已删、编号留着（`docs/M4-开发工单.md` 有完整记录）。真要实现它，
得先回答"**一种机制该怎么落成数据**"。

§10B.5 的规矩是**数据不许驱动代码分支**，所以它**不能**是一个名字数组
（那等于让数据挑选代码分支）。已经成立的那种做法是 `fridgeDead`（D-31）：
它**不是第 18 维**，而是第 2 维（腐坏速度）上的一个取值 ——
一件真的会改数值的事，挂在**已有的读数**上。

★ 判据很具体：**什么时候策划案 §10B.3.1 那张表的第 17 行能写出一个具体字段**
（而不是一个名字数组），什么时候这条才算有题意。在那之前它保持 `open`。

#### ⛔ 前置：D-28「电」是不存在的机制

6 件物品挂着 `power` tag、文案已经改成不承诺电，而**机制本身没有**。
要接上电得先回答三个设计问题（`src/meta/deferred.ts:761-766`）：
① 电从哪来（充电宝一次性？太阳能板看天气？）；② 电用来干什么
（取暖会与 `warmth` 品类打架、照明会与 `light` tag 打架、信息会与 D-13 的情报打架）；
③ 它进入日历之后，"停电"是不是一种灾难（如果是，那是一场新灾难）。

★ 这是**一次机制级新增的范围决定**，不是一笔"补齐"的账 —— 所以它和 W-10、D-35
是同一类：**先要一个答案，再要工期**。

## 4. 建议的执行顺序

```
D-33 第一步：登记新决策（§12）            ← 文档，零风险
  └─ 拍板 ①（基调方向）与 ②（日历说多少）在这里定

D-33 第二步：探针先行（四组数）            ← 改之前先量，纪律 §4A.2
D-33 第三步：:root 重定 → 边框层次复验 → windowThemes 116 组跟着重调
D-33 第四步：先知日历上移（独立提交，不与配色混在一起）

  └─ D-34 遗留：结算页"比上一局"刷新即消失（与 D-33 重画结算页一起做）

W-10  一袋米占四格    ← ⛔ 先请用户选 A / B / C，再做接线审查
D-28  电              ← ⛔ 先回答三个设计问题
D-35  第 17 维        ← ⛔ 先找出"已有读数上的取值"

第三组 1/2（NPC 囤货期露脸 + 访客来源）   ← 同一片区域，一起做
第三组 3（身份天赋等级）
第三组 4（奢侈品出口）

第四组 1/2（无障碍，成本低）
第四组 3（结局最后一页）
第四组 4（新手引导，注意 §5 的边界）
第四组 5（分享卡片）

第五组（埋点 / 内容量 / 云备份 / 移植评估）
```

★ 顺序的四条依据：

- **"改宪法"排在"改代码"之前** —— D-33 的第一步是登记决策。§5A 是设计师拍板的，
  不先立据就动手，等于把"自己改了设计师的东西"写进历史；
- **"先量后改"照旧** —— M4 的 `4869848`（配色对比拉强）就是靠先量才发现的：
  "最平的一场"跨度只有 **10.2**，而中位是 34.9 —— 只看中位数会以为没问题；
- **视觉与先知拆成两次提交** —— D-33 自己写着"不要混成一句把界面改好看"，
  而它们一个动配色、一个动信息组织，混在一起之后"哪一半让玩家觉得不同"就测不出来；
- **三条"⛔ 前置"都排在前面** —— W-10 / D-28 / D-35 缺的都是**设计答案**，
  而它们各自的答案决定后面要不要动 `SAVE_VERSION`、要不要动平衡表。
  先要答案，再要工期。

## 5. 验收口径

M5 做完时，下面每一条都要能被**量出来**（不是"感觉好多了"）：

- [ ] **视觉基调承载威胁**：页面在灾难期的**明度跨度**比现在显著更宽，
      且这条判据写成一个可复跑的探针（形如 M4 的 `scripts/_probe-contrast.ts`）；
- [ ] **三档边框层次没被暗底吃掉**：`check-style.mjs` 第 ⑧ 条（内容粗边框 ≤ 9 类）
      仍然绿，**并且**新加一条守"层次之间的对比度"—— 只数类数不验对比度，
      暗底可以把九个看起来一样的边框全部留下来；
- [ ] **116 场窗外配色跟着重调，且没有两场撞色**（M4 已有的那条守卫继续绿）；
- [ ] **先知日历在生存期的每一屏都抬头可见**，且它说的是**这一场**的信息
      （不是"寒潮"这种写死的名字）—— 用一条屏幕级测试钉住：换一场灾难，顶栏那一行跟着变；
- [ ] **320 / 375 / 390 三档零溢出**（顶栏塞进日历之后重新验）；
- [ ] **每条"⛔ 前置"要么有了设计答案、要么明确不做** ——
      不许出现第四条"登记着但没人知道该怎么办"的账。

★ 与 M4 的同一条纪律：**验收要落在断言上，不要落在手感描述上**（纪律 §6.3）。
"看起来更灾难了"必须能被翻译成一个数，否则它就不是验收项。

## 6. M5 明确**不做**的（留档，免得下次审查重新讨论一遍）

- **不重做交互手感**：M0~M2 那一轮（拖拽六条根因 + `touch-action` 三次结论）已经到位，
  M5 动的是**看**，不是**摸**；
- **不加新灾难 / 新物资 / 新事件来"撑"视觉**：视觉重构的成败与内容量无关，
  116 场已经足够验"这一场看起来是不是这一场"；
- **不给"电"和"物资尺寸"顺手造一套机制**：它们各自要先有一个设计答案（见第二组），
  顺手做出来的版本一定会在下一次审查里被记成"承诺了但没接线"（纪律 §2.19 那 6 处的形状）。
