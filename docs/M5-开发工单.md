### 2.1 W-10 物资的物理大小（"一袋米占四格"）

#### 现在的事实

- **一格 = 一个 `ItemStack`**。`src/model/types.ts:584-586`
  `export interface Slot { stack: ItemStack | null; }`；
  `ItemStack`（`:566-569`）= `{ itemId: string; batches: ItemBatch[] }`；
  `ItemBatch`（`:556-564`）= `{ expiresAtDay: number | null; count: number }`。
  一格能放几件由 `ItemDef.stackLimit`（`src/model/types.ts:74`）管。
- **没有"一件占多格"，也没有"多件不同物品占一格"** ——
  异种落同一格被 `canAccept` 明确拒（`src/model/shelf.ts:210`）。
- **面积只有一处算式**：`shelfFillRate`（`src/model/shelf.ts:469-472`）
  = `countStacks(shelf) / (shelf.w * shelf.h)`（`countStacks` 在 `:465-467`）。
  货架尺寸 `SHELF_W = 6` / `SHELF_H = 4`（`src/model/shelf.ts:11-12`），
  灾难砍排走 `rowsFor(full, factor)`（`src/systems/setup.ts:184-189`）。
- **落点判定也只有一处**：`placeHeld`（`src/systems/organize.ts:465-519`），
  放不放得下看 `roomInSlot`（`src/model/shelf.ts:193-199`）。
  交换：`swapHeldWithSlot`（`src/systems/organize.ts:577`）/ `swapSlots`（`:635`）。
- **存档就是那格矩阵**：`Shelf.slots: Slot[][]`（`src/model/types.ts:631`，`// [row][col]`），
  `SAVE_VERSION = 21`（`src/state/save.ts:89`），清洗在 `normalizeShelves`（`:1257`），
  槽位形状重建在 `:917-947`。**加"占几格"要抬到 v22 并新写一个迁移函数。**
- ★ `slotSize` 曾经存在（1=小件 / 2=大瓶 / 4=整袋），**引擎零读取**，2026-10 删除
  （`src/data/items.ts:20-22`、`src/model/types.ts:62-73`）。
  最刺的一点写在注释里：**121 条数据当时全都老实写着 1 / 2 / 4** ——
  "纯装饰比没写更坏，下一个人会以为空间是有区别的"。

#### 要回答的三个问题

1. **形状** —— 占 4 格是"**任意 4 个空格**"，还是"**相邻成块（2×2）**"，还是"**整行（1×4）**"？
   ★ 这是真正的分水岭，而且它是**三条不同的工程量**：
   - 只算格数 ≈ 把"一格一栈"换成"一格一栈 **+ 一格预算**"（改动集中在容量算式与落点判定）；
   - 成块 / 整行 = 要一个**矩形分配器**（找空位、拖动时重排、放下时校验），
     才是把"整理"变成空间谜题 —— 那正是这一笔想加厚的东西。
2. **尺寸表怎么定** —— A 只给大类定（4~5 档，121 件继承）/ B 逐件定（自由度最大，
   但要在同一次里重审价格与档位）/ C 不做（承认"一格一栈"就是终局）。
3. **叠放与批次怎么算** —— "占几格"与"一格叠几件"（`stackLimit`）是两根正交的轴。
   一袋米占 4 格之后，那 4 格里还能不能各叠 3 袋？
   （现在 `roomInSlot` 与 `mergeBatches` 都按件数算，与面积无关。）

#### 落点与代价

**五处一起动**（这就是它为什么是机制级改动）：放置（`placeHeld`）/ 合并（`mergeBatches`、
`dropStack`）/ 拖动（`swapHeldWithSlot`、`moveStack`）/ 容量（`countStacks`、`shelfFillRate`、
`autoPlace` 的选格）/ 存档（槽位形状 + v22 迁移）。

- ⚠ **归位率的分母**：`.score` 的"归位率"直接来自 `shelfFillRate`，
  "一格一栈"变成"已占格数"之后，**这个数字会整体变化**（同一局会从 40% 掉到 25% 一类）。
  它不是 bug，但它会改变玩家对"我整理得怎么样"的判断 —— 要么一起调，要么在文档里写明。
- ⚠ **旧档回填**：v21 档里没有任何"占用"信息，只能**按尺寸表回填**（或一律按 1 格读）。
  两种都要在迁移函数里写明，并且**迁移后的每一件东西占格数必须与尺寸表一致**。
- ⚠ **不许出现第二份"放得下"的判据**：现在它只有 `roomInSlot` 一处，
  加了尺寸之后最容易出现的就是"模型层算一套、UI 层算一套"。

#### 验收判据（量得出来）

- [ ] 一袋米占 4 格之后，**归位率与已占格数一致**（`countStacks` 的语义换了名字也要只有一个）；
- [ ] "放得下"在任何路径上都只走**同一处**判据（拖动 / 点击 / `autoPlace` / 从箱子里拿）；
- [ ] **v21 旧档读进来不炸**，且每件东西的占格数与尺寸表逐件一致；
- [ ] 灾难的空间维度仍然只做两件事（砍排 `rowsFor` / 摘整块 `unusableShelfIds`），**不改尺寸**；
- [ ] 有一条常驻守卫钉着"尺寸表 → 占格数"的映射（121 件逐件，不许漏一件）。

## 8. M5 明确**不做**的（留档，免得下次审查重新讨论一遍）

- **不再以任何形式加回那条进度轨**（含 `--remain` / `--ticks`）；
