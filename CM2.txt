## 一、归档 docs/归档/M3生成提示词/

6 份：总纲 / 物资 / 事件 / 灾难 / 身份与商店 / 内容参照。
它们是"曾经怎么把内容生成出来"的记录 —— 生成方 token 预算耗尽之后，
后续内容由本项目自己写，所以它们不再是现行规范，但两个用处还在：

- _内容参照.md 是**从代码导出的 id 清单**的样本（会过期：当时 17 件物资，现在 57 件）；
- 文案纪律那几段与 M3-灾难生成工单.md §3 是同一套，仍然有效。

附了一份 README 说明"别拿它当规范"，并指明现行规范在哪：
字段与区间看 node scripts/check-content.mjs --explain（读的是校验器自己的规则表，是活的），
合格判据看 npm run check。

## 二、scripts/check-content-coverage.mjs（新的常驻脚本）

从这次的一次性核对脚本提炼出来的：**每收到一批外部内容都用它过一遍**，
确认"一条都没丢，且差异只来自本项目明确做过的修订"。

它的判据是**按 id 在全库找**，不是按文件对文件 —— 这一点是踩出来的：
第一版按文件对，而灾难已经按家族重排（disaster-00 里的热浪搬去了
disaster-温度），于是它报"丢了 heat_wave / blackout_winter"，
而那两条好好地在别的文件里。**文件怎么组织是会变的，id 不会。**

更值得记的是这个脚本的 KNOWN 匹配口径我**改了三遍**，每一遍的症状都一样：
"脚本报异常，而异常其实是已知修订"。三次分别是
① 按文件对；② 拿 ^tags$ 去匹配 `tags: undefined → [...]` 整行；
③ 没注意路径带 ": " 分隔符。
**校验脚本自己的口径写错时，它的输出看起来完全正常** ——
这个形状今天在别处也踩过两次（check-content.mjs 的引号正则、
我自己那个只认单引号的计数正则）。
